# Inventory Guide

- Keep shared validation, calculations, browser transport, authorization, service, and repository code under `core/`. Keep domain types in `lib/types.ts` and page-owned UI under `app/inventory/_components/`.
- Reuse `authorizeSessionModule('inventory')` and the existing server client. Finance expense discovery and linking additionally require Finance access. Keep application tables and RPCs inaccessible to browser database roles.
- Use `inventory_mutate` for stock writes. Preserve per-owner serialization, atomic receipts, ownership filters, revisions, and nonnegative stock. Do not replace transactional operations with separate application queries.
- `delete_product` requires the current product revision and Inventory access, serializes through `inventory_mutate`, and cascades only that owned product through variants, purchase items and usages. Keep Finance transactions and other products intact. Advance surviving shared-receipt revisions to reject stale editors. The UI requires confirmation and uses shared toasts, including retryable failures.
- Inventory uses four tables: products, variants, purchase items and usages. Each `inventory_purchases` row stores one received line, its stock balance and immutable snapshot. `receipt_id` groups lines without a receipt table; grouped edits and Finance links must update every owned line atomically. Usages reference purchase-item IDs. Preserve the new `inventory_read_items` contract and the legacy read projection while deployed clients use it.
- Preserve purchase-item snapshots when products or variants change. Only unopened usable items contribute to shelf quantity. A tissue multipack expands into boxes before usage is tracked.
- Keep unknown prices and dates null. Usage states are `in_use` and `finished`; exclude incomplete usage history from estimates. Stock adjustments and item-removal actions are outside the module scope. Request receipts were removed at the owner's request. Do not reintroduce request-history storage or retry deduplication. Repeated purchases and Start using calls can apply twice; retain the in-flight button guard and revision checks. Count overlapping completed usage days once; compare countable variants only when their sheets-per-item values match.
- Run `npm run test:inventory`, `npm run test:inventory:db`, and `npm run test:inventory:browser`, followed by the root validation checks. The database suite uses an ephemeral PGlite instance with minimal dependency tables and the repository's actual module-access function and Inventory migration. It also checks the adjustment-removal migration against existing stock and its then-existing request receipts, and rejects nonempty adjustment history or removed usage states. It also verifies request-history removal, unchanged stock and RPC permissions, acceptance of older clients and repeated-save behavior. It verifies SQL behavior and permissions; it does not reproduce a multi-session production database or the entire Supabase platform.
- Keep browser fixtures under `tests/browser/` and `tests/fixtures/`. Update `document/INVENTORY_MODULE.md` and PRD 16 when behavior or rollout requirements change.
- The SQL suite also validates the populated purchase consolidation upgrade, item identities, receipt metadata, usage links, both deployed and new client contracts, canonical receipt edits and the four-table access boundary.
