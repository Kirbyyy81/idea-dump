# Screenshot-First Finance Tracking Module

## Overview

This PRD defines a new Finance Tracking module for IdeaDump focused on capturing personal finance transactions from screenshots without relying on paid bank APIs.

The first version should use a screenshot-first workflow:

- upload a transaction screenshot
- run Tesseract OCR in the app backend
- parse the extracted text into transaction candidates
- apply a deterministic rule engine
- confirm high-confidence transactions automatically
- send uncertain transactions to manual review
- use manual corrections to improve future rules

The module should treat screenshots as temporary source material, not as the long-term finance record. By default, original screenshots are processed immediately and discarded. Supabase stores durable finance data such as OCR text, image hashes, transaction candidates, confirmed transactions, rules, and correction history.

---

## V1 Implementation Decisions

These decisions are authoritative for the current v1 implementation:

| Topic | V1 decision |
|---|---|
| Access | Authenticated Member, Admin, and Owner roles may use Finance when the module is granted. Every query and write remains user-scoped. There is no public or demo Finance mode. |
| Directions | `expense` and `income` only. Transfers are outside the active v1 ledger. |
| Money dimension | Lightweight `dim_finance_sources`, not balance-bearing accounts. |
| Currency | Stored explicitly as `MYR`; v1 exposes no currency selector or exchange-rate behavior. |
| Entry route | `/finance/add` combines manual and screenshot entry. |
| OCR execution | Synchronous Next.js server processing with a 60-second route budget. |
| OCR concurrency | Different screenshots may process in parallel for the same user. Exact-image intake remains serialized and duplicate image uploads conflict, except retrying the same failed intake. |
| Candidate count | Exactly one candidate per screenshot in v1. |
| OCR retention | Raw text, normalized text, confidence, a versioned normalized-text hash, and processing metadata are retained. Original image bytes are not retained. |
| Auto-confirmation | Requires confidence of at least `0.90`, required fields, a strong active rule, and no duplicate assessment. Manual and automatic confirmation use the same transactional database operation. |
| Duplicate policy | Duplicate assessment applies to screenshot candidates. Exact image re-uploads return a conflict. Strong and possible transaction matches enter review and are never deleted automatically. Strong overrides require a reason. Ordinary manual creation and later ledger edits do not run duplicate assessment in v1. |
| Missing date | Review proposes the current date, clearly labels it as a proposal, and requires the user to confirm it. |
| Categories | Food, Drinks, Transport, and Gifts appear as virtual expense suggestions. A category is persisted only when the user explicitly adds or selects it. |
| Rule learning | The latest category correction for each current transaction is eligible evidence. Three unambiguous matches for the same normalized merchant, current category, direction, and source create a narrow active learning rule. Automatically generated rules lose active status when no longer supported. All learning rules can be paused but not permanently deleted, and paused rules are never automatically reactivated. The Rules page identifies them; no notification or broad-suggestion subsystem is created. |
| Dimension lifecycle | Sources and categories may be archived/restored. Permanent deletion requires explicit confirmation and succeeds only while completely unreferenced. |
| Dashboard | Income, spending, net cash flow, confirmed recent transactions, and pending review count are included. |

## Problem Statement

Bank and e-wallet APIs are often paid, unavailable, or too heavy for a personal self-use finance tracker. Manual finance tracking is reliable but tedious, especially when every purchase requires opening the app and entering merchant, amount, category, source, and date.

The user already receives transaction evidence through mobile banking, e-wallet, and payment screenshots. Those screenshots contain enough information to create a useful finance tracker if the app can extract text, identify the transaction details, and learn from corrections over time.

Without a dedicated module, spending information remains scattered across screenshots, bank apps, e-wallet histories, and memory. This makes it difficult to answer basic questions such as:

- how much was spent this month
- which categories are increasing
- which payments still need review
- which merchants should be categorized automatically
- which transactions are duplicates
- which recurring payments are repeating

---

## Goals

- Create a dedicated Finance Tracking module inside IdeaDump.
- Support screenshot upload as the primary v1 transaction capture method.
- Run OCR in the Next.js backend using Tesseract.
- Store OCR text and processing metadata in Supabase.
- Avoid permanent screenshot storage by default.
- Extract transaction candidates from OCR text.
- Use a backend rule engine for deterministic categorization and confirmation.
- Send low-confidence or incomplete candidates to manual review.
- Store manual corrections as feedback data.
- Use correction history to create narrow active rules after three matching category corrections for the same normalized merchant, category, direction, and source.
- Keep the architecture source-agnostic so future notification capture can feed the same intake pipeline.

---

## Non-Goals

- Direct bank API integration in v1.
- Paid transaction aggregation services in v1.
- Long-term screenshot archive storage by default.
- LLM-based transaction review in v1.
- Android notification capture in v1.
- iOS notification capture in v1.
- Multi-user shared budgets or household finance features.
- Tax, accounting, invoicing, or bookkeeping compliance workflows.
- Investment portfolio tracking.
- Payment initiation or money movement.

---

## Target User

- Authenticated users who have Finance module access through the existing Member, Admin, or Owner RBAC roles.
- Each user manages only their own Finance records; role-based module access never grants cross-user ledger access.

## Runtime Ownership

### Frontend: Next.js Browser

The frontend owns user interaction and display.

Responsibilities:

- screenshot upload UI
- optional client-side image preview
- optional client-side image compression before upload
- upload status display
- finance dashboard and charts
- transaction list and filters
- manual review queue UI
- correction forms for merchant, amount, date, source, category, reference, and direction
- category management UI
- source management UI
- rule management UI
- confidence/status display such as `Auto-confirmed`, `Needs review`, or `Duplicate`

The frontend should not create final ledger transactions directly from screenshot data. It can submit corrections and user actions, but the backend owns processing, confirmation, duplicate checks, and transaction creation.

### Backend: Next.js API Routes

The Next.js backend owns real-time finance processing logic.

Responsibilities:

- validate authenticated session and Finance module access
- receive screenshot uploads
- compute image hash for duplicate detection
- run Tesseract OCR
- clean and normalize OCR text
- parse OCR text into candidate transaction fields
- run the rule engine
- decide whether a candidate is high-confidence enough to confirm
- create confirmed transactions
- create manual review items for low-confidence candidates
- record processing events for audit/debugging
- apply manual corrections
- record correction history
- expose dashboard and transaction APIs

The backend should not rely on Supabase Storage for v1 unless temporary screenshot retention is explicitly enabled.

### Supabase Database

Supabase is the durable source of truth.

Responsibilities:

- store finance intake records
- store OCR text and cleaned text
- store image hashes
- store candidate transactions
- store confirmed transactions
- store lightweight sources
- store categories
- store rules
- store manual corrections
- store correction evidence used by narrow rule learning
- retain the existing rule-suggestion table for schema compatibility without generating new suggestion rows in v1
- store processing events
- enforce user ownership through RLS or existing server-side access patterns

### Supabase Cron

Supabase Cron owns scheduled improvement and maintenance work.

Responsibilities:

- process correction history
- promote three matching category corrections for the same normalized merchant, category, direction, and source into a narrow active rule
- detect potential duplicate transactions
- detect recurring transactions or subscriptions
- generate periodic summary snapshots if needed

Cron should improve the system over time, but it should not be required for the immediate screenshot upload flow to work.

### Future Android App

A future Android companion app should only act as a capture adapter.

Responsibilities:

- request notification access from the user
- listen to selected finance-related app notifications
- filter likely transaction notifications
- send notification text into the Finance Intake API

The Android app should not own categorization, rule execution, or ledger creation. Notification payloads should feed the same backend pipeline used by screenshots.

## Functional Requirements

### FR-001 Finance Module Registration

The system should add a new Finance module to IdeaDump's module metadata and access-control model.

Planning module slug:

```txt
finance
```

Suggested label:

```txt
Finance
```

Suggested path:

```txt
/finance
```

### FR-002 Screenshot Upload

The Finance module must allow the user to upload a screenshot containing a transaction receipt, bank notification, e-wallet payment confirmation, or transaction detail view.

The upload flow should:

- accept common image formats such as PNG, JPG, JPEG, and WEBP
- show an image preview before submission
- send the image to the backend for processing
- show processing status
- show whether the screenshot became a confirmed transaction or a review item

### FR-003 Default Image Non-Retention

Original screenshots should not be stored permanently by default.

The backend should:

- receive the uploaded image
- process it immediately
- compute an image hash
- run OCR
- store OCR text and metadata
- discard the original image after processing

If OCR fails, the system may still discard the image and ask the user to retry or manually enter details. Temporary retention is a later optional setting, not a v1 dependency.

### FR-004 OCR Processing

The backend should run Tesseract OCR on uploaded screenshots.

OCR output should include:

- raw OCR text
- cleaned OCR text
- OCR confidence if available
- processing status
- processing error message when OCR fails

The OCR service should be implemented as an adapter so it can be replaced later without redesigning the finance data model.

### FR-005 OCR Text Normalization

The backend should normalize common OCR issues before parsing.

Examples:

- trim repeated whitespace
- normalize currency symbols and `RM`
- normalize common OCR confusion such as `I2.90` vs `12.90` where safe
- preserve raw OCR text for audit/debugging

Normalization must not destroy the original raw OCR text.

### FR-006 Transaction Candidate Parsing

The parser converts normalized OCR text into exactly one candidate transaction per screenshot in v1.

Candidate fields may include:

| Field | Type | Required for Candidate |
|-------|------|------------------------|
| Amount | decimal | No |
| Currency | string | Yes; fixed to `MYR` in v1 |
| Merchant / Payee | string | No |
| Direction | enum | No |
| Transaction Date | timestamptz/date | No |
| Source Hint | string | No |
| Reference Number | string | No |
| Raw Text Match | text | Yes |
| Parse Confidence | decimal | Yes |

Confirmed direction values support:

```txt
expense
income
```

An uncertain candidate keeps direction null and goes to review rather than storing an `unknown` ledger direction.

### FR-007 Duplicate Detection

The backend should attempt to prevent duplicate transactions.

Suggested signals:

- image hash
- exact OCR text hash
- same amount, merchant, date, and source within a narrow date window
- same reference number when available

Exact image re-uploads return a conflict pointing to the existing intake. Strong and possible transaction matches always enter review in v1. The user may mark the candidate as a duplicate or explicitly override the assessment; suspected duplicates are never auto-deleted.

### FR-008 Rule Engine

The backend should run a deterministic rule engine after parsing.

Rule types may include:

- exact phrase match
- merchant alias match
- source app or bank template match
- keyword match
- amount sign/direction rule
- reference pattern rule
- source hint rule
- category mapping rule

Rules should return:

- proposed merchant
- proposed category
- proposed source
- proposed direction
- confidence adjustment
- explanation or matched rule ID

The rule engine should favor exact and user-approved rules over broad keyword matches.

### FR-009 Auto-Confirmation Threshold

High-confidence candidates may be promoted directly into confirmed transactions.

Auto-confirmation should require:

- amount detected
- direction detected or safely inferred
- category detected by a strong rule
- no duplicate conflict
- confidence of at least `0.90`

Low-confidence or incomplete candidates must go to manual review.

### FR-010 Manual Review Queue

The review queue should show candidates that could not be safely confirmed.

The user should be able to:

- edit amount
- verify the fixed `MYR` currency
- edit merchant/payee
- edit category
- edit source
- edit direction
- edit transaction date
- confirm as transaction
- reject as not a transaction
- mark as duplicate
- see whether repeated matching corrections created a learning rule on the Rules page

Review items should show the OCR text and processing notes so the user can understand why review is needed.

### FR-011 Confirmed Transaction Ledger

Confirmed transactions should be stored separately from intake and candidate records.

Transactions should support:

- amount
- currency
- direction
- merchant/payee
- category
- source
- reference number
- transaction date
- notes
- source type
- source intake ID
- confidence/source status
- created/updated timestamps

All confirmed transactions must remain editable.

### FR-012 Sources

The module supports user-defined lightweight sources. A source identifies where money was paid from or received into, but it does not track balances.

Examples:

- Cash
- Maybank
- CIMB
- TNG eWallet
- GrabPay
- Credit Card

Sources can be created, renamed, archived, and restored. Permanent deletion is allowed only after explicit confirmation and only when the source is completely unreferenced. Balance reconciliation and transfers are not part of v1.

### FR-013 Categories

The module should support suggested starter categories and user-defined categories.

Virtual starter suggestions, all of type `expense`:

- Food
- Drinks
- Transport
- Gifts

The four starter suggestions are not database rows until the user explicitly adds or selects one. Persisted categories are editable and usable by rules. A referenced category cannot change between expense and income. Permanent deletion requires explicit confirmation and succeeds only while the category is completely unreferenced.

### FR-014 Dashboard

The Finance dashboard should summarize confirmed transactions.

Suggested v1 metrics:

- spending this month
- income this month
- net cash flow
- top spending categories
- recent transactions
- pending review count

The dashboard should not depend on screenshots being retained.

### FR-015 Narrow Rule Learning

V1 rule learning has one automatic path: three matching category corrections for the same normalized merchant, category, direction, and source create a narrow active learning rule.

The generated rule must:

- use the normalized merchant as a narrow merchant-alias pattern
- retain the matching category, direction, and source
- record its supporting correction count
- be visibly labelled as learning-generated on the Rules page

V1 does not generate broad or uncertain rule suggestions and does not create editable rule drafts directly from review. The existing `finance_rule_suggestions` table may remain for schema compatibility, but no v1 job populates it. No separate notification subsystem is required.

## Processing Flow

1. User opens `/finance/add` and selects screenshot entry.
2. User selects a transaction screenshot.
3. Frontend previews the screenshot and submits it to the backend.
4. Backend validates the user session and Finance module access.
5. Backend computes an image hash.
6. Backend checks for obvious duplicate image hashes.
7. Backend runs Tesseract OCR.
8. Backend stores raw OCR text and cleaned OCR text in Supabase.
9. Backend parses OCR text into candidate transaction fields.
10. Backend runs duplicate checks using parsed fields and reference numbers.
11. Backend applies the rule engine.
12. Backend calculates final confidence.
13. A candidate meeting the `0.90` threshold, required-field, strong-rule, and no-duplicate requirements is confirmed through the transactional confirmation function.
14. Low-confidence candidate becomes a review queue item.
15. Original screenshot is discarded by default.
16. User reviews uncertain items and submits corrections.
17. Backend records corrections and updates the candidate/transaction.
18. Correction processing creates a narrow active rule after three matching category corrections for the same normalized merchant, category, direction, and source.

## Rule Engine And Feedback Loop

### Rule Engine

The rule engine should be deterministic and explainable. Every rule match should be traceable through a matched rule ID or processing event.

Suggested matching order:

1. exact template or phrase match
2. merchant alias match
3. reference or source-hint match
4. user-approved rules
5. system default rules
6. broad keyword rules

Broad keyword rules should not auto-confirm by themselves unless supported by other strong signals.

### Manual Correction Feedback

When a user confirms or edits a review item, the backend should record correction events.

Example correction:

```txt
raw OCR contains: GRAB PAY
old category: Shopping
new category: Food
old merchant: GRAB PAY
new merchant: GrabFood
```

The correction history stores the changed fields and their previous and corrected values. V1 rule learning uses category-correction evidence together with the confirmed transaction's normalized merchant, category, direction, and source.

### Rule Promotion

Supabase Cron should periodically inspect correction history.

Suggested behavior:

- three matching category corrections for the same normalized merchant, category, direction, and source create one narrow active rule
- repeated runs update the rule's evidence count without creating duplicates
- patterns that do not satisfy the exact three-correction contract create no rule in v1

Suggested safe auto-promotion example:

```txt
If exact OCR phrase contains "ZUS COFFEE" and user corrected it to Coffee 3+ times,
create an active merchant/category rule for ZUS COFFEE -> Coffee.
```

## Cron Jobs

Supabase Cron should handle background jobs after v1 ingestion works.

Suggested jobs:

### Daily Rule Learning

Runs through all retained corrections and identifies repeated safe patterns.

Outputs:

- narrow active rules backed by the exact three-correction contract
- updated learning evidence counts for existing generated rules

### Manual Review Retry

The user may retry an unresolved review item after rules change. Retry reapplies parsing, current rules, and duplicate assessment to the same pending candidate; it is not an automatic-confirmation path.

Outputs:

- updated confidence scores
- retained review state when still uncertain
- no ledger transaction until the user explicitly confirms the candidate

### Duplicate Sweep

Finds likely duplicate transactions that were not caught at upload time.

Outputs:

- duplicate flags
- review items for ambiguous duplicates

### Recurring Transaction Detection

Finds repeated merchants, amounts, and intervals.

Outputs:

- recurring transaction candidates
- dashboard insights
- future reminder opportunities

## Image Retention Strategy

### V1 Default

Do not permanently store original screenshots.

Store only:

- OCR text
- cleaned OCR text
- image hash
- processing metadata
- candidate transaction fields
- confirmed transaction fields
- correction history

This avoids depending on Supabase Storage capacity and improves privacy.

### Optional Later Modes

If review UX requires visual evidence, later versions may add:

- temporary image storage with auto-delete after 7 or 30 days
- compressed thumbnails only
- user-controlled retention setting
- external object storage such as Cloudflare R2, Backblaze B2, or S3-compatible storage

Long-term image storage should remain optional because the finance ledger should not depend on screenshot retention.

- Screenshot upload accepts PNG, JPG, JPEG, and WEBP.
- Backend runs OCR and stores raw/cleaned text.
- Original screenshot is discarded by default after processing.

The following are intentionally outside the settled v1 contract and require a later product decision before implementation:

1. Whether OCR should become asynchronous when processing volume or latency requires it.
