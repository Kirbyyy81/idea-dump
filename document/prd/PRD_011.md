# Custom Budgeting for Finance

- **Status:** Draft for approval
- **Owner:** Product and Engineering
- **Last updated:** 2026-08-31
- **Related documents:** [`FINANCE_MODULE.md`](../FINANCE_MODULE.md), [`PRD_007.md`](PRD_007.md)

## Summary

Add a personal budgeting system to Finance where users can create multiple named weekly, monthly, or custom recurring budgets. Each budget tracks net spending from selected Finance sources and categories, shows current progress and pace, and preserves frozen cycle history. The feature uses MYR, confirmed ledger transactions, and the existing Finance access model.

## Problem

Finance currently records and reports transactions but does not let users define spending limits for the periods and transaction groups that matter to them. Users cannot see whether selected spending is within a weekly or monthly target, whether spending is ahead of the cycle pace, or how completed budget cycles performed.

The product needs flexible budgets that can overlap, use source and category filters, and retain stable historical results even when older ledger data later changes.

## Goals

- Let users create and maintain multiple named budgets with independent amounts, schedules, and filters.
- Support weekly, monthly, and custom recurring cycles.
- Show current net spending, usage, remaining or over amount, elapsed pace, and status.
- Let users scope a budget to selected sources, selected categories, Uncategorised transactions, or combinations of those dimensions.
- Preserve completed and partial cycle totals and aggregate breakdowns as frozen history.
- Surface the three highest-priority active budgets on the Finance dashboard.
- Apply the existing Finance authentication, module access, ownership, validation, and security patterns.

## Non-Goals

- Blocking or declining spending.
- Shared, household, or team budgets.
- Multi-currency budgets.
- Automatic bank synchronization.
- Budget rollover, envelope transfers, or moving unused value between cycles.
- Per-transaction manual inclusion or exclusion.
- Push, email, or threshold notifications.
- Custom fiscal calendars beyond the supported recurring cycles.
- Forecasting future income or spending.
- Transaction-level snapshots for completed cycles.
- Hard deletion of budgets.

## Users and Access

| User or role | Allowed actions |
|---|---|
| Authenticated user with Finance access | View, create, edit, archive, and restore only their own budgets; view their own current progress, matching active-cycle transactions, and frozen history |
| Authenticated user without Finance access | No budget access |
| Browser role | No direct access to Finance budgeting application tables or privileged database functions |
| Trusted server | Validate ownership and references, execute approved budget functions, and return user-owned data |

## Confirmed Product Decisions

| Topic | Decision |
|---|---|
| Budget count | A user may maintain multiple budgets, including overlapping budgets. There is no fixed product limit, but list and history APIs are paginated. |
| Currency | MYR only. |
| Eligible transactions | Confirmed Finance transactions only. |
| Spending measure | Net spending equals matching expenses minus matching income. |
| Weekly recurrence | Repeat every seven days from the budget's start date. |
| Monthly recurrence | Repeat from the selected calendar day. If the day is invalid in a month, clamp that boundary to the month's last day and retain the original anchor for later months. |
| Custom recurrence | Repeat every 1 to 365 days. |
| First start | A new budget may start today or on a future calendar date. |
| Rollover | Unused value does not roll into the next cycle. |
| Overages | Progress and usage percentage may exceed 100 percent. |
| History | Completed and partial cycle totals and aggregate breakdowns are permanently frozen. |
| Overlap | The same transaction may count independently toward several budgets. |
| Feedback | Budget feedback remains inside Finance. Push and email notifications are excluded. |
| Date basis | Cycle calculations use calendar dates and transaction dates, not transaction creation timestamps. |

## User Flow

### Create a budget

1. The user opens Finance and selects Budgets from the sidebar.
2. The user selects Create budget.
3. The user enters a unique name, positive MYR amount, cycle type, start date, filter logic, and optional source and category selections.
4. The application captures the browser's IANA time zone and validates all selected references against the authenticated user.
5. The system creates the budget atomically and displays it as scheduled or active according to its start date.

### Monitor a budget

1. The user views the Finance dashboard or `/finance/budgets`.
2. The system calculates the current active cycle from confirmed matching transactions.
3. The user sees net spending, limit, uncapped usage, remaining or over amount, elapsed pace, and status.
4. On the Budgets page, the user can inspect selected filters and drill into matching active-cycle ledger transactions.

### Review history

1. The user opens a budget's details.
2. The system shows frozen cycles newest first.
3. The user can review frozen expense, income, net, source, and category breakdowns.
4. Completed cycles do not expose transaction-level snapshots.

### Archive or restore

1. The user archives an active or scheduled budget.
2. If a cycle is active, the system freezes it using transactions available at archival time and stops future cycles.
3. The archived budget remains readable in the archived section.
4. To restore it, the user provides a new start date of today or later. The restored schedule starts without changing frozen history.

1. Over budget.
2. Limit reached.
3. Needs attention.

5. Within the same status, highest usage percentage first.

- Uncapped usage percentage.
- Remaining or over amount.
- A link to the full Budgets page.

- Create, edit, archive, and restore actions.
- Current progress and elapsed cycle pace.
- Source and category filter summaries.
- Paginated cycle history, newest first.

## Counting and Matching Rules

Only transactions with `status = confirmed` whose `transaction_date` falls inside the cycle count. Periods use an inclusive start date and an exclusive next-cycle boundary.

Filter evaluation follows these rules:

- Selections within sources use OR.
- Selections within categories use OR.
- When both dimensions contain selections, apply the budget's configured AND or OR logic between the source result and category result.
- When only one dimension contains selections, use that dimension alone.
- When neither dimension contains selections, all sources and categories count, including Uncategorised.
- When categories are selected, Uncategorised counts only when explicitly selected.
- Sources and categories already selected by an active budget continue to count if later archived.
- A matching transaction may count independently toward every budget whose rules it satisfies.

For each cycle:

```text
net_spending = matching_expenses - matching_income
used_amount = max(net_spending, 0)
remaining = max(budget_amount - used_amount, 0)
over_amount = max(used_amount - budget_amount, 0)
usage_percentage = used_amount / budget_amount * 100
```

The percentage is not capped. Negative net spending is displayed, but usage remains 0 percent and remaining cannot exceed the original budget amount.

### Status rules

Status precedence is evaluated in the following order:

| Status | Rule |
|---|---|
| Scheduled | The budget's start date has not arrived |
| Over budget | Usage is greater than 100 percent |
| Limit reached | Usage is exactly 100 percent |
| Needs attention | Usage is at least 80 percent, or usage percentage exceeds the percentage of cycle days elapsed |
| On track | Usage is below 80 percent and is not ahead of elapsed cycle pace |
| Archived | The budget is archived and no longer generates cycles |

Cycle pace is based on elapsed calendar days within the cycle. It does not forecast future income or spending.

## Lifecycle Requirements

| Change or event | Required behavior |
|---|---|
| Edit name, amount, or filters | Recalculate only the active cycle from its existing start date. Completed and partial cycles remain unchanged. |
| Edit cycle type, duration, or anchor | Close the current active cycle as a frozen partial cycle through the previous calendar date, then start the revised schedule today. |
| Change schedule on the cycle's first day | Do not retain a zero-day partial cycle. |
| Edit a scheduled budget before its first cycle | Allow schedule and configuration fields to be edited freely. |
| Archive an active budget | Freeze the active cycle using transactions available at archival time and stop future cycles. |
| Archive a scheduled budget | Archive it without creating an empty active cycle. |
| Restore an archived budget | Require a new start date of today or later and begin a new schedule without modifying frozen history. |
| Add a late or backdated transaction | Recalculate an active cycle if the transaction date matches it, but do not change any frozen cycle. |
| Edit or delete an old ledger transaction | Recalculate matching active cycles only. Do not change frozen history. |
| Delete a source or category referenced by an active or scheduled budget | Block deletion. Archived references may remain represented by labels and totals in frozen history. |
| Delete a budget | Hard deletion is not available. Archive instead. |

## Data and Interfaces

### Persistence

Add a forward Supabase migration containing:

- `finance_budgets` for stable identity, ownership, name, lifecycle state, and current revision.
- `finance_budget_versions` for amount, schedule, time zone, filter logic, anchor, duration, and effective dates.
- Version-to-source and version-to-category selection tables, including explicit Uncategorised configuration.
- `finance_budget_cycles` for scheduled, active, completed, and partial cycles, including frozen expense, income, net, used, remaining, over, usage percentage, and status values.
- `finance_budget_cycle_breakdowns` for frozen source and category totals and display labels.

Persistence requirements:

- Use numeric aggregation that is safe for Finance minor units and the existing Finance amount precision.
- Enforce user ownership and valid relationships at the database layer.
- Index ownership, lifecycle state, current version, and cycle date ranges used by list and aggregation queries.
- Retain the original monthly anchor day even when an individual month's boundary is clamped.
- Store frozen labels and totals independently so history remains readable after a reference is archived or otherwise no longer active.
- Deny browser roles direct application-table access through restrictive Finance security policies and grants.
- Use atomic database functions for creation, updates, schedule replacement, archival, restoration, and cycle closure.
- Add an hourly `pg_cron` job that closes due cycles and creates successors according to each budget's stored IANA time zone.

### API contracts

| Method and route | Contract |
|---|---|
| `GET /api/finance/budgets` | List the user's active, scheduled, archived, or all budgets with current summaries and pagination as applicable |
| `POST /api/finance/budgets` | Create a budget using a client request UUID for idempotency |
| `PUT /api/finance/budgets` | Update an existing budget using optimistic concurrency protection |
| `GET /api/finance/budgets/[id]` | Return owned budget details, current cycle data, active matching transactions, and paginated frozen history |
| `PATCH /api/finance/budgets/[id]` | Archive or restore an owned budget |
| `GET /api/finance/dashboard` | Add up to three prioritized active-budget summaries without changing existing dashboard fields |

All routes must use existing Finance session authorization, request-security checks, safe JSON errors, server-derived ownership, and domain service and repository layers. Add shared Finance budget, version, cycle, status, filter, breakdown, and API response types to `lib/types.ts` during implementation.

### Idempotency and concurrency

- Budget creation requires a client-generated request UUID scoped to the authenticated user. Retrying the same accepted request returns the same budget and does not create a duplicate.
- Budget mutations require the current revision. A stale revision returns a conflict response and does not partially update the budget.
- Cycle closure and successor creation must be atomic and safe to retry.
- The hourly closure job must not create duplicate successor cycles when retried or run concurrently.

## Security and Privacy

- **Authentication:** Require a valid application session.
- **Module access:** Require Finance module access for every budget page and route.
- **Ownership:** Derive the user identity on the server. Never accept `user_id` from the browser.
- **Reference validation:** Validate every selected source and category against the authenticated user's Finance data.
- **Calculated fields:** Never accept ownership, frozen totals, breakdown values, cycle state, progress, pace, or status calculations from the browser.
- **Tenant isolation:** Prevent cross-user reads and mutations in both service logic and database policies or functions.
- **Direct access:** Browser roles receive no direct application-table access.
- **Logging:** Do not unnecessarily log budget names, transaction values, filter selections, or breakdown contents.
- **Retention:** Budget history follows the existing Finance data retention model. Hard deletion is not introduced by this feature.

## Failure and Edge Cases

| Scenario | Expected behavior |
|---|---|
| Duplicate active or scheduled name | Reject the write with a safe validation or conflict response. Archived names do not prevent a new active name unless the restore would create a conflict. |
| Invalid monthly day, such as the 31st | Clamp that month's boundary to its last calendar day and retain the original anchor for later months. |
| Leap-year February | Apply calendar-aware clamping and restore the original anchor in later valid months. |
| One-day custom cycle | Close and generate successors without duplicate or zero-length cycles. |
| Future start date | Keep the budget scheduled until its stored local start date arrives. |
| Negative net spending | Display the negative net value, use 0 percent usage, and cap remaining at the budget amount. |
| Usage over 100 percent | Show the full uncapped percentage and over amount. |
| Schedule edit on first day | Replace the schedule without retaining a zero-day partial cycle. |
| Late or backdated ledger entry for a frozen cycle | Leave the frozen cycle unchanged. |
| Old ledger transaction edited or deleted | Leave frozen cycles unchanged and recalculate only affected active cycles. |
| Referenced source or category is archived | Continue counting it for an active budget and retain its frozen history labels. |
| Referenced source or category deletion requested | Block deletion while an active or scheduled budget references it. |
| Concurrent edit | Reject the stale mutation with a conflict response and ask the user to reload. |
| Closure job retry or overlap | Return or preserve the existing closed cycle and single successor without duplication. |
| Time zone becomes invalid | Reject new or edited configuration. Existing invalid data must fail safely and be observable to operators without exposing private budget data. |
| Empty list or missing history | Show the appropriate accessible empty state without treating it as an error. |

## Delivery

- **Migrations:** Add new forward migrations only. Do not rewrite an applied Finance migration or the adopted baseline.
- **Environment:** No new browser secrets. Enable and configure the approved Supabase `pg_cron` schedule through migration or documented deployment configuration.
- **Deployment order:** Apply the database migration and functions, verify policies and scheduled closure behavior, then deploy application APIs and UI.
- **Compatibility:** Existing Finance dashboard and transaction interfaces remain compatible. The dashboard budget field is additive.
- **Documentation:** Update [`FINANCE_MODULE.md`](../FINANCE_MODULE.md) during implementation with the delivered model, routes, lifecycle rules, and operating requirements.
- **Rollback:** Disable new application entry points and the cron schedule before reverting application usage. Preserve created budget and frozen history data unless a separately approved data migration removes it.
