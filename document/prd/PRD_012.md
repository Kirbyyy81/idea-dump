# PRD: External Project Knowledge Hub

- **Status:** Very early draft
- **Owner:** Product
- **Last updated:** 2026-08-31
- **Related documents:** None

## Summary

Create a private project-knowledge workflow that keeps personal technical documentation outside work repositories. Codex would retrieve and update the documentation through an external documentation service, while Idea Dump may later provide a private, read-only viewing experience. This PRD captures the idea only and does not schedule implementation.

## Problem

Technical knowledge about work projects is difficult to preserve when it exists only as Markdown inside development environments or as personal notes mixed into source repositories. Committing personal documentation to a work repository may confuse other developers, while keeping it only in an editor makes it harder to read, revisit, and maintain.

Important business rules, API behaviour, module logic, and development decisions may therefore be lost or become outdated. There is no current personal system that lets Codex recover this context across development sessions, maintain it as the implementation changes, and present it in an easy-to-read private interface.

## Goals

- Keep personal technical documentation outside work source repositories.
- Give Codex a consistent external source from which it can retrieve and update project documentation.
- Preserve business logic, module behaviour, API knowledge, and important development decisions.
- Record what changed in the documentation, when it changed, and why.
- Support requirements described by the user from a concept paper without requiring the complete source document to be uploaded.
- Support converting API specifications and other supplied files into structured, readable documentation when needed.
- Allow Idea Dump to become a private documentation viewer in a possible later phase.

## Non-Goals

- Replacing official company documentation.
- Committing the personal documentation to work repositories or GitLab.
- Uploading complete concept papers by default.
- Treating a user summary of a concept paper as a direct quotation or authoritative copy of the original.
- Publishing work documentation publicly.
- Automatically updating documentation after every code change without user direction.
- Building a collaborative documentation platform for teams.
- Providing documentation editing through Idea Dump in the initial version.
- Selecting Notion as the final provider before its capabilities and company acceptability are verified.

## Users and Access

| User or role | Allowed actions |
|---|---|
| Owner | Retrieve, view, create, and update personal project documentation; connect projects to external documentation; review change and decision history |
| Codex acting for the owner | Retrieve and update authorized documentation, record decisions, and create change-log entries within the requested project scope |
| Unauthenticated visitor | No access |
| Idea Dump server | Read only the external documentation explicitly shared with its private integration |

## User Flow

### Record a requirement during development

1. The owner opens the relevant work project in Codex.
2. The owner describes the applicable requirement or business logic from a concept paper.
3. Codex retrieves the existing external project documentation and inspects the available implementation.
4. Codex distinguishes user-provided requirements, verified implementation behaviour, development decisions, assumptions, and unresolved questions.
5. Codex updates the relevant documentation and creates a dated change-log entry.

### Update documentation at a development checkpoint

1. The owner asks Codex to update the project knowledge after completing a feature, integration, bug fix, or other meaningful checkpoint.
2. Codex compares the current implementation with the existing documentation.
3. Codex updates only the affected modules and records any material decision or discrepancy.
4. The owner reviews the resulting documentation in the external service.

### View documentation through Idea Dump

1. The owner signs in to Idea Dump and opens a linked project.
2. Idea Dump retrieves or displays a synchronized read-only representation of the related documentation.
3. The owner browses module documentation, API information, decisions, and change history.
4. The owner may open the source page in the external documentation service when needed.

## Requirements

| ID | Requirement | Acceptance |
|---|---|---|
| FR-001 | Store documentation outside the source repository | Project documentation can be created, retrieved, and maintained without adding documentation files to the related work repository. |
| FR-002 | Retrieve documentation by project and module | Codex can locate the authorized documentation for a named project or module without requiring the full content to be pasted into every session. |
| FR-003 | Update living technical documentation | Codex can update business rules, technical flows, integrations, validations, edge cases, and known limitations at the owner's request. |
| FR-004 | Preserve provenance | Documentation distinguishes user-described requirements, code-verified behaviour, development decisions, assumptions, and AI interpretation. |
| FR-005 | Record decisions | A material development decision can be recorded with its context, selected option, reason, tradeoffs, consequences, related module, and date. |
| FR-006 | Maintain a readable change log | Every Codex documentation update can add a dated summary identifying what changed, why it changed, and what evidence was used. |
| FR-007 | Support concept-derived requirements | The owner can describe relevant concept-paper content and have it converted into structured requirements without uploading the complete paper. |
| FR-008 | Avoid unsupported invention | Codex identifies material ambiguity and does not invent missing business rules or claim that an unverified interpretation is confirmed. |
| FR-009 | Support API documentation | When the owner provides an API file or description, Codex can produce structured documentation covering the relevant authentication, endpoints, payloads, errors, mappings, and business behaviour. |
| FR-010 | Preserve original source status | When a source file is provided, generated documentation is identified as a derived representation and does not silently replace the original as the authoritative source. |
| FR-011 | Provide private Idea Dump viewing | In a later phase, an authenticated owner can view linked external documentation from the related Idea Dump project. |
| FR-012 | Keep website access read-only initially | The first Idea Dump integration cannot modify external documentation. Editing remains in the external service or through an explicitly authorized Codex workflow. |
| FR-013 | Reflect external updates | A later synchronization mechanism can refresh the Idea Dump representation after the external documentation changes. |
| FR-014 | Protect provider credentials | External service credentials remain in trusted server environments and are never exposed to browser code or public responses. |

## Data and Interfaces

The final provider and data model are intentionally undecided. A possible future structure includes:

- **Projects:** Stable project identity and external documentation relationship.
- **Documentation:** Module, API, concept-derived requirement, and overview pages.
- **Decisions:** Append-only decision records related to projects and modules.
- **Change log:** Dated documentation changes with source and verification status.
- **Source references:** Optional links or attachments for API files and other materials provided by the owner.
- **Idea Dump mapping:** A relationship between an owned Idea Dump project and one or more external documentation page identifiers.
- **Viewer cache:** An optional normalized copy used only to display content efficiently in Idea Dump. The external platform remains the source of truth.

Potential interfaces include an external documentation connector for Codex, a server-side provider API for Idea Dump, and a webhook or manual refresh operation for later synchronization.

Idempotency, synchronization ownership, conflict handling, and provider-specific identifiers must be defined if implementation is scheduled.

## Security and Privacy

- **Authentication:** Idea Dump viewing requires an authenticated application session.
- **Authorization:** Only the owner and explicitly authorized integrations may access linked documentation.
- **Provider access:** Each integration receives the minimum required access. The Idea Dump integration should be read-only initially.
- **Sensitive data:** API secrets, credentials, customer data, personal data, and other restricted material must not be copied into documentation or logs.
- **Work information:** The owner must confirm that company information may be stored in the selected external service and accessed by Codex or Idea Dump.
- **Logging:** Provider tokens, source document contents, temporary file URLs, and private documentation payloads must not be logged.
- **Browser exposure:** Provider credentials and unrestricted provider responses must never be sent to the browser.
- **Deletion and retention:** Provider history, Idea Dump cache retention, and deletion behaviour must be defined before implementation.

## Failure and Edge Cases

| Scenario | Expected behavior |
|---|---|
| External documentation is unavailable | Codex or Idea Dump reports that current documentation could not be retrieved and does not replace it with guessed content. |
| Project or module cannot be matched | The user is asked to identify the correct documentation target before an update is made. |
| User description conflicts with the implementation | The documentation records the discrepancy and does not silently choose one version as correct. |
| Requirement is ambiguous | Codex records an open question or asks for clarification when the ambiguity would materially change the behaviour. |
| Concept-paper description is incomplete | Generated content is marked as user-provided and incomplete rather than presented as a complete concept-paper summary. |
| API file is unsupported, scanned, or malformed | Codex reports the limitation and preserves the original file or reference when available. |
| External update occurs while Codex is editing | The workflow avoids silently overwriting newer content and identifies the conflict for review. |
| Idea Dump synchronization fails | The last successfully synchronized content remains visible with a stale-status indicator and retry option. |
| Provider attachment URL expires | Idea Dump requests a fresh authorized URL rather than retaining or exposing an expired temporary link. |
| User lacks company approval | Work documents are not moved to the external system until an approved storage option is selected. |

## Delivery

This feature is not scheduled. The following phases describe a possible future sequence only.

### Phase 1: Workflow validation

- Select an approved external documentation provider.
- Test retrieving and updating a harmless sample project through Codex.
- Confirm page creation, editing, search, permissions, history, and attachment behaviour.
- Define the documentation, decision, and change-log structure.

### Phase 2: Personal Codex workflow

- Create a reusable personal documentation workflow or skill.
- Support development-checkpoint and project-wrap-up updates.
- Require provenance and change-log entries.

### Phase 3: Idea Dump viewer

- Add project-to-documentation mappings.
- Add a private, read-only documentation view.
- Render supported documentation and source references.
- Add search, filtering, synchronization status, and safe failure states.

### Phase 4: Synchronization

- Add provider webhooks or another approved refresh mechanism.
- Cache normalized content if required for performance and availability.
- Define conflict, retry, retention, and deletion behaviour.

- **Migrations:** None until implementation is approved.
- **Environment:** Provider-specific server credential and documentation identifiers may be required later. Final variable names are undecided.
- **Deployment order:** Provider setup, database mapping and policies, server integration, then authenticated viewer.
- **Rollback:** Disable synchronization and the viewer while preserving external source documentation. Any disposable viewer cache may be removed through a separately reviewed migration.

## Verification

No implementation verification is required while this PRD remains an idea. If scheduled, verification should include:

- **Automated:** Provider client parsing, authorization, project mapping, Markdown or block conversion, webhook validation, synchronization retries, stale-cache behaviour, and safe error tests.
- **Browser:** Authenticated project documentation navigation, desktop and mobile reading, search, source links, empty states, stale states, and access denial.
- **Data:** Ownership isolation, provider-page mapping, cache provenance, synchronization timestamps, and deletion behaviour.
- **Workflow:** Codex retrieves an existing sample page, updates a single module, records provenance, creates a decision when required, and appends one change-log entry without modifying the source repository.

## Open Decisions

- Which external documentation provider is approved and best suited to the workflow?
- Is a personal Notion workspace permitted for the intended work information?
- Which Codex surface will be used during development, and does it support the selected provider connection?
- Should Codex update documentation only on explicit request, or should any repeatable automation be introduced?
- Should Idea Dump read directly from the provider or use a synchronized Supabase cache?
- How should an Idea Dump project map to external project, module, decision, and change-log pages?
- Which API file formats should be supported first?
- Should supplied source files be stored, linked, or discarded after the derived documentation is created?
- What retention and deletion rules apply to cached documentation and change history?
- Should Idea Dump remain permanently read-only for documentation?
