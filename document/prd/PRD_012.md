# PRD: External Project Knowledge Hub

- **Status:** Draft, planning
- **Owner:** Product
- **Last updated:** 2026-09-23
- **Related documents:** None

## Summary

Create a private project-knowledge workflow with Notion Free as the main documentation store outside work repositories. The first working release includes Codex reading and updating documentation at the owner's request, Markdown and PDF exports, a Versions section preserving the initial baseline and every Codex update, and a private Idea Dump viewer for the latest document contents. The knowledge hub is independent of Idea Dump's existing Projects module. Optional project relationships are maintained in Notion and do not require Idea Dump project records. Historical snapshots are browsed in Notion; this PRD defines the release scope without scheduling implementation.

## Problem

Technical knowledge about work projects is difficult to preserve when it exists only as Markdown inside development environments or as personal notes mixed into source repositories. Committing personal documentation to a work repository may confuse other developers, while keeping it only in an editor makes it harder to read, revisit, and maintain.

Important business rules, API behaviour, module logic, and development decisions may therefore be lost or become outdated. There is no current personal system that lets Codex recover this context across development sessions, maintain it as the implementation changes, and present it in an easy-to-read private interface.

## Goals

- Keep personal technical documentation outside work source repositories.
- Give Codex a consistent external source from which it can retrieve and update project documentation.
- Preserve business logic, module behaviour, API knowledge, and important development decisions.
- Record what changed in the documentation, when it changed, and why.
- Let the owner refer back to documentation versions throughout the entire lifetime of a project.
- Provide portable exports without requiring an editable Markdown copy in the work repository.
- Keep documentation storage, history, exports, and the connection free of additional subscription, paid API, or hosting charges.
- Support requirements described by the user from a concept paper without requiring the complete source document to be uploaded.
- Support converting API specifications and other supplied files into structured, readable documentation when needed.
- Let the owner read the complete latest feature documentation directly inside Idea Dump through a private, read-only viewer in the first working release.
- Let the owner browse documentation without creating, linking, or maintaining projects in Idea Dump.

## Non-Goals

- Replacing official company documentation.
- Committing the personal documentation to work repositories or GitLab.
- Uploading complete concept papers by default.
- Treating a user summary of a concept paper as a direct quotation or authoritative copy of the original.
- Publishing work documentation publicly.
- Automatically updating documentation after every code change without user direction.
- Building a collaborative documentation platform for teams.
- Providing documentation editing through Idea Dump in the initial version.
- Managing Notion projects or their document relationships through Idea Dump, or synchronizing them with Idea Dump's Projects module.
- Maintaining two-way synchronization with an editable local Markdown copy.
- Supporting other coding agents in the initial workflow.
- Automatically recording every direct edit made in Notion as a separate archived version.
- Browsing historical snapshots through Idea Dump in the initial version; the owner uses Notion for that history.
- Automatically refreshing the open Idea Dump document in the background in the initial version.

- **Workspace:** Use the owner's existing Notion workspace and the selected [Document Hub database](https://app.notion.com/p/3e4bb9f9e5f9800b9762c22c8c63824c?v=3e4bb9f9e5f98088bf08000cf9065789), inside the Documentation Database page, as the destination for current feature documents. The database identifier is `3e4bb9f9-e5f9-800b-9762-c22c8c63824c`; its data source identifier is `3e4bb9f9-e5f9-8086-81f8-000be9e74ae7`. This replaces the earlier Resources destination. Codex MCP authentication and read access were verified on 2026-09-23; document writes and the separate Idea Dump server connection still need validation.
- **Primary copy:** The current documentation lives in Notion. Local files are optional exports.
- **Project independence:** The knowledge hub has no dependency on Idea Dump's Projects module or project records. Documentation may have optional project links or grouping inside Notion. Those relationships are maintained in Notion or through an explicitly requested Codex workflow; Idea Dump only reads them when useful for browsing.
- **Export formats:** Markdown for portability and PDF for reading or sharing. Both formats must be available through the free workflow.
- **Feature structure:** Each feature has one main Notion page containing its entire documentation as readable page content, including headings, tables, code examples, and diagrams. Architecture, APIs, decisions, and other feature sections stay together on that page.
- **Version navigation:** Each feature page links to its own Versions section containing the initial baseline and dated full snapshots. The main page always represents the latest documentation.
- **Agent:** The Codex desktop app is the initial interface for reading and updating documentation, using the authenticated Notion MCP connection at `https://mcp.notion.com/mcp`. Read access to Document Hub and its template is confirmed; creation, targeted updates, history capture, and exports remain to be validated.
- **Trigger:** Codex reads or updates documentation when the owner asks. An update request includes retrieving the existing documentation needed for that update.
- **History:** Preserve an initial baseline and a dated full snapshot for every Codex documentation update in a Notion Versions section. The owner can refer to those versions throughout the project's lifetime, including years later.
- **Capture boundary:** The owner accepts a version for every Codex update. Automatic capture of every direct Notion edit is outside the initial scope.
- **Historical agent access:** Codex access to older versions is preferred, but is not a blocker. Access to current documentation remains required.
- **Idea Dump viewer:** Required in the first working release alongside the Codex and Notion workflow. An authenticated owner can read the complete latest document within Idea Dump, with headings, tables, code examples, diagrams, and links. The initial viewer is read-only and historical snapshots are browsed in Notion.
- **Viewer refresh:** Load the latest Notion content whenever the owner opens a document, with a Refresh button available while reading. Background refresh is outside the initial scope.
- **Cost:** The documentation workflow must operate on free services and features.
- **Reference content:** The supplied example is a detailed feature document containing architecture, flows, state, API contracts, mappings, decisions, limitations, verification cases, source references, and maintenance guidance. The workflow must preserve this depth and structure.

### Confirmed history approach

As checked on 2026-09-16, Notion Free provides seven days of native page history. The agreed Versions section stores snapshots as ordinary Notion content so the workflow can retain them beyond that native history window. See [Notion's version-history limits](https://www.notion.com/help/duplicate-delete-and-restore-content).

The owner has accepted this custom archive. Save the initial document as a baseline, then retain one dated full snapshot for each completed Codex documentation update, linked to the current document and its change-log entry. Treat a requested documentation update as one logical revision even if it requires several provider calls. Earlier archived versions remain unchanged by later documentation updates.

The archive covers Codex update checkpoints. Direct edits in Notion are included when Codex next reads and saves the current document, but each intermediate manual edit is not captured separately. Snapshot identifiers, attachment and link preservation, and recovery from partially completed updates remain to be defined before implementation. A documentation update is complete only when its current content, snapshot, and change-log entry have all been saved and verified.

| User or role | Allowed actions |

| Owner | Retrieve, create, and update documentation and optional project relationships in Notion or through Codex; read current documents through Idea Dump; review change and decision history in Notion |

## User Flow

### Import existing documentation

1. The owner identifies the Markdown document and its feature title, with an optional project relationship inside Notion.
2. Codex imports the entire authorized feature document into one main page in Document Hub as readable content, preserving its technical detail, structure, source references, and existing verification metadata. The complete document belongs in the page body, with its title and categorization in the database properties.
3. Codex saves the initial baseline in Versions, and the owner checks the resulting document and an export for content and formatting fidelity.
4. Future requested reads and updates use the Notion document as the main copy.

### Record a requirement during development

1. The owner opens the relevant work project in Codex.
2. The owner describes the applicable requirement or business logic from a concept paper.
3. Codex retrieves the existing external project documentation and inspects the available implementation.
4. Codex distinguishes user-provided requirements, verified implementation behaviour, development decisions, assumptions, and unresolved questions.
5. Codex updates the relevant documentation and creates a dated change-log entry.
6. Codex saves and verifies a full snapshot of the resulting document in Versions.

### Update documentation at a development checkpoint

1. The owner asks Codex to update the project knowledge after completing a feature, integration, bug fix, or other meaningful checkpoint.
2. Codex compares the current implementation with the existing documentation.
3. Codex updates only the affected modules and records any material decision or discrepancy.
4. Codex saves and verifies a dated full snapshot and its change-log entry.
5. The owner reviews the resulting documentation and can browse earlier snapshots in Notion.

### Refer to an earlier version

1. The owner opens a document's Versions section in Notion.
2. The owner selects the baseline or an earlier Codex update by date and change summary.
3. Notion displays the full saved content for that checkpoint without changing the current document.
4. Where supported by the selected connection, the owner can also ask Codex to retrieve or compare archived versions.

### View documentation through Idea Dump

1. The owner signs in to Idea Dump and opens the independent knowledge hub.
2. The owner browses or searches the authorized Notion documents and selects a feature document. Optional project grouping comes from Notion; no Idea Dump project record is required.
3. Opening the document triggers an authorized read of its latest Notion content. Idea Dump renders that content within the website, preserving headings, tables, code examples, diagrams, links, and document metadata.
4. The owner reads the complete current document, including its module behaviour, API information, and decisions. The owner uses Notion to browse saved historical snapshots.
5. While reading, the owner can select Refresh to fetch the latest Notion content again. The view shows when it was last fetched and labels any fallback copy as stale if a fetch fails.
6. The owner can open the source page in Notion when needed.

### Viewer experience requirements

- Provide a readable view of the complete feature document inside Idea Dump. A document title, summary, attachment link, or link to Notion alone is insufficient.
- Provide a document browsing entry point independent of Idea Dump's Projects module. Any displayed Notion project relationships are read-only and optional.
- Preserve the feature document's section order and provide navigation within long documents.
- Support desktop and mobile reading, including wide tables, long code examples, and diagrams.
- Show loading, empty, unavailable, and stale-content states where applicable, with a retry or refresh action.
- Keep Notion as the source of truth and use authenticated, authorized access to its private content.
- Read the latest authorized Notion content when the document opens and whenever the owner selects Refresh. Show the last successful fetch time and preserve a clearly labeled stale fallback only when a current fetch fails and a cached copy is available.

## Data and Interfaces

Notion is the selected provider and source of truth. Each feature has one main documentation page in Document Hub and a linked Versions section. Optional project organization lives in Notion; the knowledge hub does not use Idea Dump project records as its identity, ownership, or navigation model. Document Hub's existing schema was inspected on 2026-09-23: `Doc name` is the title, `Projects` is an optional single-project Notion relation, `Select` categorizes entries as `Technical Documentation` or `API`, and `Created by` and `Created time` are system-managed. Its default `New doc` template contains generic Background, Analysis, Recommendations, and Implementation sections; imports must preserve each feature document's complete structure. The Versions archive layout and any supporting viewer schema remain undecided. A possible future supporting structure includes:

- **Notion project references:** Optional project pages, relations, or labels used to organize documentation within Notion. Documents do not require an Idea Dump project relationship.
- **Documentation:** One complete main page per feature in Document Hub, containing its overview, architecture, module behaviour, API details, concept-derived requirements, and decisions as applicable. Database properties provide metadata; the page body contains the full readable document.
- **Decisions:** Append-only decision records related to projects and modules.
- **Change log:** Dated documentation changes with source and verification status.
- **Versions:** An archive of the initial baseline and full documentation snapshots for each Codex update, linked to the current Notion page and change-log entry. Each snapshot needs a stable identity, date, and readable change summary; its final schema remains to be defined.
- **Source references:** Optional links or attachments for API files and other materials provided by the owner.
- **Idea Dump document access:** An owner-scoped configuration identifying the selected Document Hub database, its data source, and authorized document identifiers. Discovery and access are independent of Idea Dump project records; the final configuration and storage mechanism remain undecided.
- **Viewer cache:** An optional normalized copy used only to display content efficiently in Idea Dump. The external platform remains the source of truth.

Interfaces include the authenticated Notion MCP connection for the Codex desktop app and a planned server-side Notion API integration that retrieves document content for Idea Dump. The viewer reads from Notion when a document opens or the owner selects Refresh. Any normalized cache must follow that freshness contract; its implementation remains undecided. Notion supplies the documentation store and Idea Dump supplies the required website viewer.

Idempotency, synchronization ownership, conflict handling, and provider-specific identifiers must be defined if implementation is scheduled.

## Security and Privacy

- **Authentication:** Idea Dump viewing requires an authenticated application session.
- **Authorization:** Only the owner and explicitly authorized integrations may access configured documentation. Access is checked independently of Idea Dump project membership or records.
- **Provider access:** Each integration receives the minimum required access. The Idea Dump integration should be read-only initially.
- **Sensitive data:** API secrets, credentials, customer data, personal data, and other restricted material must not be copied into documentation or logs.
- **Work information:** The owner must confirm that company information may be stored in the selected external service and accessed by Codex or Idea Dump.
- **Logging:** Provider tokens, source document contents, temporary file URLs, and private documentation payloads must not be logged.
- **Browser exposure:** Provider credentials and unrestricted provider responses must never be sent to the browser.
- **Private rendering:** Notion documents remain private. Idea Dump authorizes access to each linked document on the server and safely renders the allowed content without requiring public Notion sharing.
- **Deletion and retention:** Preserve documentation history for the entire documented project's lifetime. Archiving or deleting an Idea Dump project has no effect on Notion documentation, history, or viewer access. Explicit documentation deletion behaviour, the treatment of archived Notion projects, source attachments, and any Idea Dump cache retention must be defined before implementation.

## Failure and Edge Cases

| Scenario | Expected behavior |
|---|---|
| External documentation is unavailable | Codex or Idea Dump reports that current documentation could not be retrieved and does not replace it with guessed content. |
| Project or module cannot be matched | The user is asked to identify the correct documentation target before an update is made. |
| User description conflicts with the implementation | The documentation records the discrepancy and does not silently choose one version as correct. |
| Requirement is ambiguous | Codex records an open question or asks for clarification when the ambiguity would materially change the behaviour. |
| Concept-paper description is incomplete | Generated content is marked as user-provided and incomplete rather than presented as a complete concept-paper summary. |
| API file is unsupported, scanned, or malformed | Codex reports the limitation and preserves the original file or reference when available. |
| External update occurs while Codex is editing | The workflow avoids silently overwriting newer content and identifies the conflict for review. |
| An old version is outside Notion Free's native history window | The chosen archive must preserve access to that version; a change-log summary alone is insufficient. |
| A requested update cannot preserve the required history | Report the incomplete operation and preserve the existing documentation. Define retry and recovery behaviour before implementation. |
| The owner edits a document directly in Notion | Codex reads the latest content before its next requested update. The Versions section covers Codex checkpoints and does not claim to capture each intermediate manual edit. |
| Idea Dump synchronization fails | The last successfully synchronized content remains visible with a stale-status indicator and retry option. |
| Provider attachment URL expires | Idea Dump requests a fresh authorized URL rather than retaining or exposing an expired temporary link. |
| User lacks company approval | Work documents are not moved to the external system until an approved storage option is selected. |

Phases 1 through 3 are implementation work areas that must all be completed for the first working release, including the Codex workflow, history, exports, and the Idea Dump viewer. Phase 4 describes possible later synchronization enhancements; a working refresh mechanism for the current-document viewer is required in Phase 3.

### Phase 3: Idea Dump viewer

- Configure owner-authorized Notion document discovery and access independently of Idea Dump's Projects module.
- Add an independent knowledge-hub entry point; display optional Notion project grouping without project-management controls.
- Add a private, read-only view that renders complete feature documents inside Idea Dump.
- Render headings, tables, code examples, diagrams, links, metadata, and source references.
- Add long-document navigation, search, filtering, the last successful fetch time, and safe failure states.
- Fetch the latest authorized document on open and on Refresh, with retry and a clearly labeled stale fallback when a current read fails and cached content is available.

### Phase 4: Optional synchronization enhancements

- Add provider webhooks or another approved refresh mechanism.
- Cache normalized content if required for performance and availability.
- Extend the initial conflict, retry, retention, and deletion rules as needed for optional synchronization changes.

- **Migrations:** None until implementation is approved.
- **Environment:** The Codex workflow uses the authenticated Notion MCP connection and selected Document Hub identifiers. The required Idea Dump viewer needs its own server-side Notion connection; Codex authentication does not establish viewer access. Final configuration names are undecided.

- **Rollback:** Disable the documentation workflow and Idea Dump viewer while preserving the current Notion documents and saved Versions. Disable any optional synchronization. Any disposable viewer cache may be removed through a separately reviewed migration.
