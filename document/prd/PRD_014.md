# PRD: Log Viewer Barcode Generator

- **Status:** Implemented; physical scanner acceptance pending
- **Owner:** Ashley
- **Last updated:** 2026-10-02
- **Related documents:** [Log Viewer](../LOG_VIEWER.md), [Design System](../DESIGN_SYSTEM.md), [Repository guide](../../AGENTS.md)

## Summary

Add a Barcode Generator subpage under Log Viewer that automatically generates a Code 128 barcode from a numeric identifier for scanning directly from the screen. Keep the seven most recent distinct generated identifiers in a sidebar using browser session storage. No generation button, history cleanup controls, printing, downloads, or server-side history are required.

## Problem

Ashley currently switches to an external barcode generator, enters an identifier, and scans the resulting barcode. The supplied screenshot shows Code 128. Bringing this workflow into IdeaDump removes the application switch and makes recently used identifiers available without retyping them.

## Goals

- Generate a scannable Code 128 barcode automatically after numeric input settles.
- Keep up to seven recently generated identifiers available for immediate reuse.
- Preserve identifiers exactly, including leading zeros and values beyond JavaScript's safe integer range.
- Keep generation and temporary history on the user's device.
- Fit the tool into Log Viewer navigation and its existing access permissions.

## Non-Goals

- Printing, downloading, exporting, or copying barcode images.
- Manual Generate or Refresh buttons.
- Individual history deletion or a Clear history action.
- Other barcode formats, format selection, letters, or escape-sequence interpretation in the initial version.
- Batch generation, label design, sequential-number generation, or camera-based scanning.
- Database history, cross-device synchronization, or live synchronization across tabs.
- Automatic identifier extraction from logs or changes to log parsing.
- Embedding the external generator or sending identifiers to its service.
- Guaranteed offline launch of the application.

## Users and Access

| User or role | Allowed actions |
|---|---|
| Signed-in user with Log Viewer module access | Open the generator, enter identifiers, scan the preview, and reuse their tab's recent identifiers. |
| Signed-in user without Log Viewer access | Cannot access the generator through navigation or its direct URL. |
| Signed-out user | Follow the existing authentication flow before access. |

The existing `/log-viewer` route-prefix rule maps nested pages to `log_viewer`. Reuse the existing app shell and authorization checks. Do not create a separately permissioned module.

## User Flow

1. User opens **Log Viewer > Barcode Generator** at `/log-viewer/barcode-generator`.
2. User types or pastes a numeric identifier into one text field.
3. After a short pause, the application validates the value and automatically displays its Code 128 barcode with the exact identifier underneath.
4. User scans the barcode directly from the screen using their existing scanner.
5. The successfully generated value appears at the top of **Recent numbers**. The list retains at most seven distinct values.
6. Selecting a recent value fills the input, immediately regenerates its barcode, and moves that value to the top.
7. Refreshing or navigating away and back in the same tab retains history. A normal tab close ends the session history.

## Requirements

### Confirmed product choices

Ashley confirmed the following on 2026-10-02: the generator is a Log Viewer subpage; generation is automatic; there are no history cleanup controls; barcodes are scanned from the screen without print or export actions; typical input is numbers only; and the last seven values can disappear when the tab closes. Code 128 is the initial format based on the supplied workflow screenshot.

The timing, duplicate handling, and layout details below are proposed implementation defaults, not additional choices explicitly supplied by Ashley.

| ID | Requirement | Acceptance |
|---|---|---|
| FR-001 | Add Barcode Generator beneath Log Viewer in navigation. Preserve an accessible entry to the existing Log Viewer page. | Both `/log-viewer` and `/log-viewer/barcode-generator` are reachable; the appropriate navigation item is active on each page. |
| FR-002 | Use one styled text input with a numeric keyboard hint. Treat its value as a string throughout. | Leading zeros and long numeric values survive input, generation, storage, and recall without rounding or scientific notation. |
| FR-003 | Trim surrounding whitespace, then accept only a nonempty sequence of ASCII digits `0-9`, up to 256 digits to bound rendering work. | Oversized input is rejected without truncation. Pasted surrounding whitespace is ignored; internal spaces, punctuation, letters, line breaks between digits, and escape sequences are rejected rather than silently rewritten. |
| FR-004 | Automatically generate after 400 ms without an input change. Cancel superseded pending work. | Typing and pasting produce a preview without Enter, blur, or a button. Rapid edits produce only the final settled result. |
| FR-005 | Never leave a previous barcode visible as though it represents newly edited input. | On an input change, hide the previous barcode until the current value successfully generates. Empty or invalid input shows no scannable preview. |
| FR-006 | Render Code 128 using automatic encoding selection, with black bars, an opaque white background, sufficient quiet zones, and readable identifier text. | Light and dark themes both retain the same high-contrast barcode surface. The encoded value and displayed text match exactly. |
| FR-007 | Prioritize direct screen scanning and preserve barcode geometry. | Bars are not cropped, stretched, or compressed to force a fit. If width exceeds the preview, allow horizontal scrolling and a concise instruction to use a wider viewport; supported workflow identifiers must fit fully on the target scanning screen. |
| FR-008 | Add history only after successful generation of settled input. | Invalid input, rendering failures, and keystrokes within the debounce window create no history entries. |
| FR-009 | Keep the seven most recent distinct canonical values, newest first. | Generating an eighth distinct value evicts the oldest; generating an existing value moves it to the front without duplication. `00123` and `123` remain different entries. |
| FR-010 | Selecting a recent value regenerates immediately and cancels any pending input generation. | One selection fills the field, displays the selected barcode, and updates recency without an additional action or a later stale result. |
| FR-011 | Show Recent numbers in a compact right-hand sidebar on desktop and below the generator on narrow screens. | All seven values are accessible by pointer and keyboard, with the selected value indicated. Long values remain available in full. |
| FR-012 | Provide no history removal, print, export, download, or manual generation controls. | The page contains only the controls necessary to enter and reuse identifiers. Users can edit or empty the input normally without deleting history. |
| FR-013 | Persist recent values in user-scoped browser session storage. | Refresh and same-tab navigation preserve history; a fresh independent tab starts empty; normal tab closure ends retention. No identifier is written to the application database or persistent local storage. |
| FR-014 | Keep the tool usable when session storage is unavailable or malformed. | Use bounded in-memory history for the mounted page if storage fails; show concise persistence status when needed. Invalid stored content cannot crash the page or render unvalidated values. |
| FR-015 | Follow existing app components, design tokens, and accessibility conventions. | The input has a visible label, errors are associated with it, history entries are keyboard-operable buttons, and the preview exposes its identifier as accessible text. |

The 400 ms pause is a heuristic for completed entry. If the user pauses longer while typing a partial but valid numeric identifier, it can generate and enter history. No fixed identifier length has been established, so the application must not guess completeness from length. Do not add a manual confirmation step to resolve this limitation.

## Data and Interfaces

- **Route:** `/log-viewer/barcode-generator`, within the existing `log_viewer` module.
- **Generation:** Use a bundled browser-side barcode library such as [JsBarcode](https://github.com/lindell/JsBarcode), which supports Code 128 and SVG output. Verify the chosen package version and license during implementation. Use no remote generator or runtime CDN dependency.
- **Rendering:** Prefer SVG for crisp rendering. Preserve module proportions, white margins, and the full human-readable identifier. Validate actual scanner compatibility before treating rendered appearance as sufficient evidence.
- **History shape:** A versioned record containing at most seven identifier strings ordered by recency. Store values, not barcode images. Use the existing domain-type conventions if shared types are introduced.
- **Storage key:** A feature-specific, versioned key scoped to the authenticated user, for example `idea-dump:barcode-generator:v1:<user-id>`.
- **Retention:** Use `sessionStorage`, with no database records, cookies containing identifiers, IndexedDB, or `localStorage` history. Normal tab closure clears the session; browser session restore or tab duplication can restore or copy session storage. This is temporary convenience storage, not a guaranteed secure-erasure boundary. See [sessionStorage behaviour](https://developer.mozilla.org/en-US/docs/Web/API/Window/sessionStorage).
- **Account changes:** Clear the departing user's feature history and visible state on sign-out or account switch. Never render another user's stored values.
- **Restore:** Validate the record version, shape, and each stored string; deduplicate and cap to seven. Restore the recent list, leaving the input and preview empty until entry or selection.
- **Duplicate handling:** Equality uses the trimmed digit string. Do not convert to numeric values or collapse leading zeros.
- **APIs and migrations:** None required. Existing authentication and authorization remain in use.

## Security and Privacy

- Generate barcodes locally; do not send input or history to analytics, application logs, error-report payloads, or external barcode services.
- Keep identifiers out of URLs, query strings, and navigation state that could expose them through links or request logs.
- Enforce existing Log Viewer access for direct route visits as well as navigation visibility.
- Treat stored values as untrusted input and render them through normal text and barcode APIs, never injected markup.
- Clear pending generation and visible history when the authenticated user changes.

## Failure and Edge Cases

| Scenario | Expected behavior |
|---|---|
| Empty or whitespace-only input | Empty preview, no validation error, and no history update. |
| Unsupported characters or multiple pasted identifiers | Concise numbers-only error; no barcode and no history update. |
| Leading zeros or an identifier longer than the safe integer range | Preserve the exact digit string throughout. |
| Rapid edits or selecting history while a generation is pending | Cancel superseded work; only the current value may update preview or history. |
| User pauses mid-entry | A valid settled prefix may generate; document and test this known debounce behavior. |
| Eighth distinct identifier | Remove the oldest history entry automatically. |
| Rendering failure | Hide the preview, show a concise error, preserve input, and do not update history. |
| Barcode wider than the viewport | Preserve geometry and quiet zones; allow scrolling and advise a wider viewport. Do not claim a clipped barcode is ready to scan. |
| Storage blocked or corrupt | Continue generation; retain safe bounded history in memory or recover valid entries as appropriate. |
| Normal tab close followed by a fresh tab | Start with empty history. Session restore and duplicated tabs follow the browser caveat above. |
| Navigation away during the debounce window | Cancel pending generation; already recorded history remains available in the same tab. |

## Verification

- **Automated behavior:** Test exact-string preservation, whitespace handling, invalid values, debounce cancellation, stale-preview removal, failed generation, seven-item eviction, deduplication, immediate recall, malformed storage, storage failure, and user/session isolation.
- **Browser:** Verify automatic generation without a click or Enter, keyboard interaction, recent-item selection during pending input, refresh, same-tab navigation, fresh-tab isolation, sign-out/account switching, access denial, light/dark themes, and desktop/mobile layouts. Confirm identifier data causes no network requests.
- **Barcode correctness:** Decode generated barcodes with an independent decoder where feasible and compare with the original digit strings. Include leading-zero, odd-length, even-length, and long synthetic identifiers.
- **Physical acceptance:** Ashley scans representative workflow identifiers directly from the actual display with the usual scanner. Verify exact scanned output, including leading zeros, and full barcode visibility. Record the device, browser, scanner, and tested lengths. Visual inspection alone does not establish scanning success.
- **Implementation checks:** Run `npm audit`, `npm audit --omit=dev`, `npm run lint`, `npx tsc --noEmit`, `npm test`, and `npm run build`. Run `npm run test:log-viewer`, `npx playwright test tests/browser/log-viewer.spec.ts`, and the new barcode browser coverage for the Log Viewer navigation and interaction changes.
- **PRD-only checks:** Check document formatting, relative links, consistency with confirmed scope, and `git diff --check`. Application test suites are required when implementation changes are made, not for this documentation-only delivery.
