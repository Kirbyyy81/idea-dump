# PRD: Shared Finance Category Learning

- **Status:** Draft, planning
- **Owner:** Ashley
- **Last updated:** 2026-10-05
- **Related documents:** [Finance Module](../FINANCE_MODULE.md), [Finance PRD](PRD_007.md), [Android Companion PRD](PRD_013.md), [Companion Integration](../ANDROID_COMPANION.md), [Parser Learning Rollout](../FINANCE_PARSER_LEARNING_ROLLOUT.md), [Design System](../DESIGN_SYSTEM.md)

## Summary

Learn a user's preferred category for a merchant or payee after one explicit category selection, then apply it to future matching screenshot and notification transactions across that user's Finance sources. Keep expense and income separate, preserve manual-rule precedence, and learn only from human choices. Provide controls to inspect, pause, and resolve conflicting mappings without changing historical transactions.

## Problem

The current screenshot and notification learners improve extraction but do not learn category preferences. Both pipelines can apply manually configured category rules, while a category selected during review or transaction editing currently affects only that transaction.

The previous category learner was retired by `20260915172224_retire_legacy_finance_learning.sql`. Its refresh is a no-op and database guards prevent new or reactivated legacy learning rules. The replacement extraction systems intentionally exclude categories, leaving no active category learner.

This means repeatedly categorizing the same cafe does not teach future transactions. Complete notifications may be saved automatically as Uncategorised even after the user categorized earlier transactions at that merchant.

Category preferences must be independent of bank message and receipt formats. The same notification format can describe a cafe, supermarket, or petrol station; learning a category for the whole format would assign unrelated transactions incorrectly.

## Goals

- Activate an unambiguous category mapping after one explicit human selection committed successfully.
- Reuse the mapping across screenshots, notifications, and Finance sources belonging to the same user.
- Separate merchant from payee identities and expense from income.
- Apply a learned category only when no applicable manual rule already assigns one.
- Make every learned assignment traceable to a mapping and its human evidence.
- Prevent automatic assignments, retries, and repeated evidence for one transaction from teaching the system.
- Allow conflicting preferences, category lifecycle changes, and evidence edits to stop unsupported assignments immediately.

## Non-Goals

- Learning categories from bank wording, notification formats, receipt templates, amounts, or dates.
- AI or external classification services, industry-wide merchant categories, fuzzy merchant matching, or cross-user training.
- Replacing screenshot parser learning or notification extraction patterns.
- Re-enabling, converting, or importing the retired category-learning rules.
- Source-specific category preferences in this release. The confirmed scope is across the user's sources.
- Automatic category creation or automatic merchant/payee alias discovery.
- Reclassifying historical transactions, bulk training from existing records, or automatically retrying pending items.
- Changing duplicate linking, screenshot automatic-confirmation requirements, Android capture, or APK distribution.

## Users and Access

| User or role | Allowed actions |
|---|---|
| Authenticated user with Finance access | Teach categories through their own successful Finance actions; inspect, pause, enable, and resolve their own category mappings. |
| Paired Android companion | Continue uploading authorized notification events using the existing contract; cannot select categories or create learning evidence. |
| Authorized application and OCR service | Read owner-scoped mappings; apply categories with provenance. Only trusted human-action RPCs may record training evidence. |
| Other users or unauthenticated callers | No access to another owner's mappings, supporting transactions, or mutations. |

## User Flow

### A. Teach a category

1. The user chooses a category while reviewing a screenshot or notification, creating a manual transaction, or editing an existing confirmed transaction.
2. The transaction saves through its normal validated, duplicate-aware workflow.
3. The server records the explicit selection and the transaction's final merchant/payee identity and direction. One eligible selection activates a mapping immediately.
4. The UI reports that the category was remembered for future matches, or explains why it remains transaction-only, such as a conflict or missing counterparty.

Selecting Food & Drinks for an expense at KEFI KOHI teaches that merchant's expense category. A later screenshot from TNG or notification from Ryt can use Food & Drinks even when its amount, date, or receipt format differs.

A category already filled by a manual or learned rule does not become evidence merely because the user presses Confirm or edits an unrelated field. An explicit Remember this category action can acknowledge an unchanged suggestion. A newly selected category counts without requiring a second confirmation.

### B. Use an existing mapping

1. The existing pipeline extracts and validates transaction fields, resolves payee identity, and applies manual Finance rules.
2. If no manual rule assigns a category, the shared learner looks up an enabled, supported category mapping for the final counterparty and direction.
3. A unique active mapping supplies the category and provenance. Missing, conflicting, invalid, or paused mappings leave the category unset.
4. Existing duplicate checks and confirmation policies run. A complete notification may auto-add with the category, but this automatic result creates no training evidence.
5. Explicit Retry uses the same current mappings. Existing pending items are not updated in the background.

### C. Resolve a different category choice

1. The user selects another category for the same identity and direction.
2. That transaction saves with the user's selection. Its current evidence replaces any earlier evidence from the same transaction.
3. If valid evidence from other transactions disagrees, the mapping becomes Conflicted. Neither majority voting nor the most recent transaction silently chooses the category.
4. Finance settings offers the supported categories and their evidence. Choosing one for future matches starts a new evidence generation; older conflicting preferences are superseded for learning without changing their transactions.
5. A later contradictory explicit selection can conflict again. The user can instead pause the mapping when the merchant regularly spans multiple categories.

### D. Manage learned categories

1. Open Finance, Settings, Rules, Learned categories.
2. Inspect counterparty, merchant/payee classification, direction, category, scope, supporting transaction count, state, and last change.
3. Open an owned supporting transaction, pause or enable a mapping, or resolve a conflict using a currently supported category.
4. Settings and review use the shared app components and remain usable on mobile. Retired legacy rules stay separately identified.

## Requirements

### Product decisions

Ashley confirmed on 2026-10-05:

- One explicit category selection is sufficient to activate learning.
- A learned category applies across the user's Finance sources.
- Expense and income remain separate.

The conflict and lifecycle behavior below are proposed requirements for this draft. They do not change the approved thresholds or scope.

| ID | Requirement | Acceptance |
|---|---|---|
| FR-001 | Separate category preference learning from screenshot extraction templates and notification patterns. | Learning Food & Drinks for one cafe cannot categorize all messages using the same bank format. |
| FR-002 | Activate after one eligible human selection, without a scheduled promotion job. | The next matching intake after the successful commit receives the category. |
| FR-003 | Scope by owner, merchant/payee identity, and direction, across sources and intake channels. | A Ryt notification teaches a later TNG screenshot for that owner; another owner's transaction and an income transaction do not match. |
| FR-004 | Train from successful manual creation, manual review confirmation, or explicit category edits on confirmed transactions. | Each supported human flow creates or replaces one current transaction evidence record. |
| FR-005 | Distinguish explicit selection from a prefilled category. | Unchanged automatic/manual-rule suggestions, general confirmation, notes-only edits, and API payload echoes create no evidence; explicit acknowledgement can. |
| FR-006 | Use final validated counterparty and direction, with conservative, versioned identity matching. | Unicode names work; differences in amount, date, reference, bank, or receipt layout do not change identity. Distinct merchant/payee kinds never match. |
| FR-007 | Apply existing manual rules before learned category assignment. | A matching manual category wins; a manual rule assigning only another field does not block a learned category. A user's explicit choice wins on the transaction being saved. |
| FR-008 | Share category lookup between screenshot processing, notification intake, and their explicit Retry paths. | Equivalent final identities receive the same category and provenance in every path. |
| FR-009 | Count each confirmed transaction at most once. | Request replay, multiple intakes, or screenshot evidence linked to a notification do not increase support. |
| FR-010 | Exclude automatic confirmation, rejection, duplicate resolution/linking, unsuccessful saves, and uncommitted UI choices from training. | These actions create no category evidence even when their payload includes a category. |
| FR-011 | Pause learned assignment when current evidence supports different categories. | Conflicting mappings assign neither category; the saved transaction retains the user's chosen category. |
| FR-012 | Allow explicit conflict resolution for future transactions. | Owner selects a currently supported category with a revision check; historical ledger values remain unchanged and older conflicting evidence is superseded. |
| FR-013 | Keep pause state independent of evidence validity. | Later reviews may update evidence but never silently enable a paused mapping. Enable is rejected if the category is unusable or a conflict remains. |
| FR-014 | Update or invalidate support when its transaction changes or is deleted. | Correcting its category replaces its vote; clearing category, changing identity/direction without an explicit new selection, or deleting it removes its support and recomputes affected mappings. |
| FR-015 | Handle category and payee lifecycle changes. | Archived/deleted categories cannot be assigned. A category rename preserves its ID-based mapping. Invalid or ambiguous payee identity cannot supply a learned category. |
| FR-016 | Record category provenance separately from parser and manual-rule provenance. | Review can distinguish Learned category from Manual rule and an unset category without mislabeling extracted fields. |
| FR-017 | Revalidate a learned assignment when persisting a candidate or automatically confirming a transaction. | A category archived or mapping paused/changed during processing cannot silently retain stale learned output. |
| FR-018 | Preserve existing auto-confirmation and duplicate policy. | Learned categories do not bypass duplicate warnings or satisfy screenshot requirements for a strong manual rule. Notifications can still auto-add Uncategorised when their required fields are valid. |
| FR-019 | Do not treat clearing a category as a learned Uncategorised preference. | Clearing removes that transaction's support; the UI offers pausing the mapping for future matches. |
| FR-020 | Do not train automatically from historical corrections or previously resolved records. | Deployment changes zero historical transaction categories and imports zero legacy evidence; a new explicit category action on an old transaction can train. |
| FR-021 | Expose owner-scoped inspection and management in Finance settings. | Mappings show enabled state, eligibility, source scope, category, direction, and safe links to current evidence. |
| FR-022 | Keep human saves and training state atomic and idempotent. | Unexpected database failure rolls back both; a semantic ineligibility such as missing counterparty saves the transaction with an explicit no-learning outcome. |

### Identity and conflict policy

- Use saved, active, owned payee IDs when available. Unresolved payee names use a versioned normalized name key and remain separate from saved-ID mappings until an explicit identity reconciliation is designed.
- Merchant names use a conservative category-specific key: Unicode NFKC, consistent apostrophes, case folding where available, and collapsed whitespace. Preserve meaningful punctuation, digits, accents, and uncased scripts such as Chinese. Do not remove branch/location suffixes or infer aliases.
- Reuse existing identity helpers only where their semantics satisfy these requirements. Current merchant/payee lookup helpers discard some characters; do not alter existing payee matching or replay identities simply to introduce category keys.
- Merchant and payee are distinct identity kinds. If classification is unresolved or both parties are present without a clear transaction counterparty, do not teach or apply a mapping.
- A single latest explicit selection per transaction contributes to the current generation. Matching evidence from two transactions counts as two; screenshots and notifications describing one linked transaction count as one.
- Updating the only supporting transaction from category A to B can replace the mapping with B. If another current supporting transaction still chooses A, the mapping becomes Conflicted.
- Editing only source, amount, date, reference, or notes does not create fresh support. Source changes do not invalidate otherwise valid support because mappings apply across sources.
- Renaming a saved payee keeps its ID-based mapping; deletion or archiving makes it unusable. Do not silently merge name-based or previously conflicting identities.
- Category archival makes its evidence unusable. Restoring a category re-evaluates current evidence, but never overrides an explicit pause. Deleting it permanently removes usable support while retaining only necessary safe provenance.
- Resolving a conflict requires valid supporting evidence for the selected category. A new unsupported preference is created through an explicit transaction selection or an ordinary manual rule.

## Data and Interfaces

### Proposed data

Final SQL names may be adjusted during implementation; the separation and guarantees are required.

| Store | Purpose and required fields |
|---|---|
| `finance_category_mappings` | Owner; identity kind and key; normalization version; direction; nullable category; enabled flag; eligibility state (active, conflicted, unsupported, category unavailable); revision; evidence generation; timestamps. Unique mapping scope across sources. |
| `finance_category_evidence` | Owner; supporting confirmed transaction; mapped identity and direction; explicitly selected category; human action type; mutation/idempotency identifier; evidence generation; validity and timestamps. Enforce one current contribution per owned transaction. |
| Candidate and transaction provenance | Assignment origin, mapping ID/revision when learned, and human selection status needed for review and commit validation. Keep historical attribution separate from whether the mapping is usable today. |

Persist category preference state separately from legacy `finance_rules.source = 'learning'`. Do not bypass retirement guards, label automatically learned rows as manual rules, or mix category evidence with notification raw text or OCR parser evidence.

Use owned foreign keys, scoped indexes, bounded names/keys, and revision checks. Keep domain types in `lib/types.ts`. Derive support counts and status from valid evidence under the same mutation lock; they must not drift from supporting transactions.

### Proposed interfaces and integration

- Add a shared, runtime-independent category matcher for application and OCR consumers. Keep credentialed reads and mutations in existing repository/service boundaries.
- Add owner-scoped `GET /api/finance/category-mappings` for a bounded, paginated mapping list and `PATCH` for pause/enable/conflict resolution using mapping ID and expected revision.
- Extend existing manual create, review-confirm, and transaction-edit contracts with a typed category action: unchanged, explicitly selected, or explicitly acknowledged. Missing action in older clients means no new training.
- Authenticate the action through the existing human Finance routes. Derive owner, transaction identity, category validity, confirmation mode, and permitted operation server-side; a companion or OCR payload cannot declare itself human.
- Wrap or version the existing confirmation and transaction RPCs so a successful ledger mutation, evidence replacement, and mapping recalculation commit together. Preserve notification extraction learning, raw-text deletion, duplicate locks, and screenshot correction recording.
- Reuse the per-user Finance ledger lock and a consistent lock order. Concurrent category changes, mapping management, and auto-confirmation must use the same serialization and revision checks.
- In both intake pipelines, complete extraction and payee resolution, apply manual rules, then apply category learning only if category is still unset, followed by duplicate assessment and normal persistence/confirmation.
- Do not overwrite the existing manual `matched_rule_id` with a category-mapping identifier. Learned category provenance has its own field.
- Do not apply a learning lookup to overwrite a manually chosen category on save. Automatic prefilling in the manual-entry form is outside this initial scope; manual entry is an evidence source.
- Read learned mappings in bounded batches for a single owner, not one database query per OCR field. Revalidate references and revision at persistence rather than trusting a long-lived cache.

**Idempotency:** The existing transaction/review mutation identity governs training. Same request replay returns the original result without another vote; a changed payload using the same key conflicts. Duplicate linking may invalidate evidence if it changes the final supporting identity/category, but it never creates or amplifies support. Invalidated evidence cannot be reconstructed from deleted notification text.

**Retention:** Retain only structured identities, category choices, and the transaction/action provenance needed to explain current mappings. Delete or invalidate support as part of the transaction lifecycle, cascade account deletion, and keep bounded superseded-generation metadata without copying full transaction payloads.

## Security and Privacy

- **Authentication:** Existing signed-in Finance sessions for human actions and settings; existing trusted service authentication for lookup. No new Android credential scope.
- **Authorization:** Reuse Finance RBAC and repository clients. Enforce owner checks on every source, category, payee, transaction, mapping, and evidence reference. RLS and server-only grants cover the new stores and mutation RPCs.
- **Sensitive data:** Do not retain full notification messages, screenshots, OCR excerpts, account details, or references for category learning. Logs and metrics contain outcomes and IDs rather than counterparty names or transaction text.
- **Mutation safety:** Use established CSRF/request protections, validation, size limits, revisions, and idempotency. Browser-supplied category-action metadata cannot bypass transaction eligibility or permissions.
- **Isolation:** A user's explicit choices never train another user, and rejected or sensitive notifications remain excluded by the existing filters.

## Failure and Edge Cases

| Scenario | Expected behavior |
|---|---|
| Same merchant, different bank or amount | Reuse the category within the owner's direction scope. |
| Same counterparty, income versus expense | Maintain independent mappings. |
| Two similar names, changed branch suffix, or unresolved payee | Require the exact supported identity; leave unmatched category unset. |
| User confirms a prefilled category without explicitly selecting or acknowledging it | Save normally without new training evidence. |
| A manual rule disagrees with a learned mapping | Manual rule wins for intake; UI identifies its provenance. Editing one transaction does not silently rewrite the manual rule. |
| Two current human examples disagree | Save the selected category on each transaction and pause learned assignment until conflict resolution. |
| One supporting transaction is edited or deleted | Replace or remove that contribution atomically and recompute both old and new scopes where applicable. |
| Mapping paused, then new matching review confirmed | Keep it paused; record eligible evidence without reactivation. |
| Category is archived, deleted, or unavailable | Do not assign it. Show unavailable state in settings. |
| Supporting screenshot is linked to an existing notification transaction | Keep a single ledger transaction and do not add a training vote. |
| Mapping changes after parsing | Recompute or clear learned output before persistence; preserve manual assignments and use current duplicate/confirmation policy. |
| Mapping query or database write fails | Do not silently claim learning succeeded. Return a retryable processing/save failure; preserve intake durability and mutation idempotency. |
| Notification has all required fields but no usable category | Existing notification policy may auto-add Uncategorised; the user can teach it later through an explicit edit. |
| Screenshot receives only a learned category | It remains subject to existing screenshot confidence and strong manual-rule gates; learning alone does not authorize auto-confirmation. |
| Old client sends no category action | Keep existing transaction behavior and create no training evidence. |
| Historical rule/evidence lacks new provenance | Do not import it or infer that it was a new explicit human choice. |
