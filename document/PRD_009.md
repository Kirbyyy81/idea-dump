# Android Multi-File Share-to-Finance OCR

## Overview

This PRD defines an Android share-to-app enhancement for the existing Finance OCR workflow.

An authenticated user with Finance access can select between one and ten screenshots or supported images in another Android application, share them to the installed IdeaDump PWA, review the received file list on the existing `/finance/add` page, remove unwanted files, and confirm the batch.

Before confirmation, the shared files remain in browser memory only. After confirmation, the PWA uploads the files to private temporary Supabase Storage and creates a durable server-side batch queue. Once every accepted file is safely uploaded and queued, the UI tells the user that the PWA may be closed. Render then processes the files serially in the background through the existing Finance OCR pipeline.

Each image represents exactly one independent Finance transaction candidate. A failure or duplicate in one image does not prevent the remaining images from being processed.

Original image bytes are temporary operational input only. They are never shown in Finance review and are deleted as soon as every item in the batch reaches a terminal result.

## Problem Statement

The current Finance intake flow requires the user to open IdeaDump, navigate to Finance, select a single screenshot, and wait for the synchronous OCR request.

Android users often capture several transaction screenshots while using banking, e-wallet, receipt, or messaging applications. Returning to IdeaDump and submitting those screenshots one at a time creates unnecessary work.

The synchronous single-image flow also requires the user to remain in the request. That behavior is unsuitable for a shared batch because processing up to ten screenshots serially may take long enough for the user to close or leave the PWA.

The product needs a low-friction Android share flow that:

- accepts multiple explicitly shared images
- asks for confirmation before processing
- preserves current Finance validation and decision rules
- hands confirmed work to a durable background queue
- allows the PWA to close after durable handoff
- does not retain screenshots after the batch finishes
- does not require paid infrastructure

---

## Goals

- Register the installed IdeaDump PWA as an Android image share target.
- Accept one to ten PNG, JPEG, or WebP images from one Android share action.
- Reuse `/finance/add` as the share confirmation and active-batch surface.
- Keep shared images in browser memory only before confirmation.
- Allow the user to remove individual images before processing.
- Require one explicit confirmation action before uploading or processing.
- Upload confirmed images to private temporary Supabase Storage.
- Create a durable server-side queue before telling the user that the PWA may close.
- Process each image independently and serially through the existing Render Finance OCR pipeline.
- Create exactly one Finance transaction candidate per image.
- Auto-confirm only candidates that meet the existing `0.90` Finance policy and all safeguards.
- Route uncertain candidates and terminal failures into the existing submitting user's Finance review experience.
- Detect exact image duplicates by the existing per-user image hash, report them, and skip redundant processing.
- Delete all temporary images immediately after the complete batch reaches terminal state.
- Remove transient batch and queue state after cleanup.
- Preserve the existing free-tier-only operating constraint.

---

## Non-Goals

- iOS share-target support.
- Desktop share-target support.
- Sharing more than ten images in one batch.
- Supporting PDFs, HEIC, video, text, links, or non-image files.
- Combining several images into one transaction.
- Extracting several transactions from one image.
- Permanently retaining original screenshots.
- Showing original images in manual review.
- Storing unconfirmed shared images on the server or in Supabase Storage.
- Resuming an unconfirmed share after the PWA is closed or reloaded.
- Anonymous or public Finance intake.
- Automatically continuing a share after login.
- A separate batch-history page.
- Push notifications.
- Email notifications.
- A new in-app notification subsystem.
- Cross-user review, reviewer assignment, or administrative review.
- Image crop, rotation, enhancement, replacement, or annotation tools.
- Increasing Render OCR concurrency above one.
- A paid Render worker, paid queue, paid cache, persistent disk, or paid OCR provider.
- Changing the ordinary single-image upload flow defined by `PRD_008`.

## Target User

- An authenticated Android user who has Finance module access through the existing RBAC model.
- The user has installed the IdeaDump PWA so Android can present it as a share target.
- The user submits and reviews only their own Finance records.

Member, Admin, or Owner module roles do not grant cross-user Finance access. Every batch, intake item, temporary object, candidate, transaction, and review result remains scoped to the submitting user.

## Module Scope

### Primary Areas

1. Android Web Share Target registration
2. Shared-file capture in the PWA service worker
3. Authentication and Finance-access check
4. `/finance/add` share confirmation mode
5. Private temporary batch upload
6. Durable batch queue creation
7. Serial Render OCR consumption
8. Existing Finance parsing, duplicate, rule, and confirmation pipeline
9. Active batch status on `/finance/add`
10. Existing Finance review integration
11. Terminal image and batch cleanup

### Route Contract

The feature reuses the existing Finance route structure:

```txt
/finance/add       share confirmation and active batch status
/finance/review    existing candidate review plus failed intake items
/finance/transactions
```

The PWA manifest may use a dedicated POST action endpoint for receiving Android shares, but that endpoint must redirect or hand off to `/finance/add`. It is an ingestion endpoint, not a new user-facing batch route.

## Runtime Ownership

### Android and Installed PWA

Android owns:

- screenshot capture
- image selection
- native share-sheet presentation
- delivery of the selected files to the installed PWA

The installed PWA owns:

- registration as an image share target
- interception of the incoming multipart POST
- temporary in-memory transfer of the shared `File` objects to the foreground page
- opening `/finance/add` in share confirmation mode

The service worker and foreground page must not persist unconfirmed image bytes in Cache Storage, IndexedDB, the application database, Supabase Storage, or another server.

### Next.js Browser Experience

The browser UI owns:

- validating that a current authenticated session exists
- confirming that the user has Finance module access through the existing application contract
- displaying the received file list
- showing validation failures
- allowing individual files to be removed
- requesting explicit batch confirmation
- uploading confirmed files to private temporary Storage
- requesting one authoritative batch-and-queue commit
- withholding the safe-to-close message until durable handoff succeeds
- showing the current active batch automatically when `/finance/add` is opened
- displaying batch and per-file progress while the batch exists

The browser must never receive a Supabase service-role key, Supabase secret key, Render secret, or unrestricted queue credential.

### Next.js Server

The Next.js server owns the authenticated control-plane operations required to:

- verify the current user and Finance access
- validate batch membership and ownership
- issue narrowly scoped upload authorization or perform trusted uploads
- verify that every confirmed object exists at its expected private path
- create the transient batch and batch-item records
- enqueue one opaque message per accepted image
- trigger the best-effort Render wake-up
- return durable handoff success only after the batch and queue messages exist
- expose the submitting user's active batch status
- expose failed intake items through the existing Finance review API

The server must use existing Supabase clients and RBAC guards. It must not trust a browser-supplied `user_id`, storage path, batch owner, or processing status.

### Supabase Storage

Supabase Storage owns only temporary bytes for a confirmed, actively processing share batch.

Requirements:

- use a private bucket
- scope every path to the authenticated user and generated batch/item identifiers
- deny public access
- deny cross-user reads, writes, listing, and deletion
- never use a user-provided filename as the authoritative storage path
- make Render access server-controlled
- delete every object when the batch reaches terminal state

Suggested path shape:

```txt
{userId}/finance-share-batches/{batchId}/{batchItemId}/original.{extension}
```

The original filename may be retained as sanitized Finance source-detection evidence, but it must not determine ownership or the generated object path.

### Supabase Postgres and Queue

Supabase owns:

- transient batch and batch-item state
- one durable queue message per accepted image
- authoritative user ownership
- processing-attempt count
- queue visibility and redelivery after an interrupted consumer
- durable Finance intake, candidate, transaction, duplicate, and failed-intake records
- idempotent finalization
- recovery detection for queued or stale work

Queue messages must contain opaque identifiers only. They must not contain screenshot bytes, bearer tokens, signed URLs, OCR text, or trusted user identity supplied by the browser.

### Render Finance OCR Service

Render owns:

- authenticated consumption of queued Finance work
- serial processing with one active OCR operation
- server-controlled download of the expected temporary image
- full current image validation
- image hashing
- Tesseract OCR
- normalization and parsing
- source inference
- Finance rule evaluation
- duplicate assessment
- auto-confirm eligibility
- idempotent Finance finalization
- immediate second attempt after a recoverable first-attempt failure
- terminal failure recording after two total attempts
- queue-message completion

Render must continue using the runtime-neutral Finance processing pipeline defined by `PRD_008`.

## Functional Requirements

### FR-001 PWA Share Target Registration

The PWA manifest must register one Android file share target that:

- uses `POST`
- uses `multipart/form-data`
- accepts multiple files under one field name
- accepts PNG, JPEG, and WebP
- routes the share to the PWA ingestion handler

The application must appear in the Android share sheet only when the PWA is installed and the platform supports Web Share Target.

The existing manifest remains the source for the IdeaDump name, icons, colors, display mode, start URL, and scope.

### FR-002 Shared POST Handling

The service worker must intercept the share-target POST and read the incoming multipart files.

It must:

- ignore unsupported text, title, and URL data for Finance ingestion
- pass the incoming files to the foreground Finance add experience
- redirect or navigate to `/finance/add`
- keep the files in memory only
- avoid writing the files to the current offline cache
- reject or report malformed shared content safely

The foreground page cannot assume that the sending application provided trustworthy MIME types, extensions, filenames, or file counts.

### FR-003 Authentication and Finance Authorization

Before presenting a processable confirmation state, the application must verify:

- an active authenticated Supabase session
- current Finance module access

If the user is signed out:

1. Discard every incoming file from memory.
2. Navigate to sign-in.
3. Explain that the user must share the images again after signing in.
4. Do not create anonymous batch, intake, object, or queue records.

If the user is authenticated but lacks Finance access:

1. Discard every incoming file.
2. Show an access-denied result.
3. Do not upload or process the images.

### FR-004 File Count and Format Limits

One share action may contain between one and ten processable images.

Each accepted file must follow the current `PRD_008` image contract:

- PNG, JPEG, or WebP
- maximum 4 MB per image
- declared MIME type consistent with magic bytes
- safe decoded image
- maximum width and height matching the current Finance OCR limit
- maximum decoded pixel count matching the current Finance OCR limit
- non-empty content

There is no separate combined batch-size setting. Because at most ten files of 4 MB each are accepted, the effective maximum is 40 MB.

Invalid files must be identified individually so the user can remove them while retaining valid files from the same share action.

### FR-005 Share Confirmation Mode

When launched from the Android share target, `/finance/add` must show a confirmation mode containing:

- the received image list
- validation result for each image
- filename and size for each image
- an individual remove action
- the remaining valid-image count
- one explicit action to process the remaining images

No OCR, Finance intake, batch, queue message, or server-side image storage may be created before the user confirms.

If the user closes or reloads the PWA before confirmation, the in-memory files are lost and nothing requires cleanup.

### FR-006 Confirmation Handoff

After the user confirms:

1. Revalidate the authenticated session and Finance access.
2. Revalidate the remaining file count and per-file byte/type contract.
3. Generate server-authoritative batch and item identifiers.
4. Upload every accepted file to the private temporary bucket.
5. Verify the expected objects.
6. Create the transient batch and item state.
7. Enqueue one durable message for each accepted image.
8. Trigger the background consumer.
9. Return a durable-handoff result to the browser.

The UI must not state that the user may close the PWA until every accepted image is present in private Storage and has a durable queue message.

If durable handoff is incomplete, the UI must remain truthful, identify the submission problem, and must not imply that background processing will continue.

### FR-007 Active Batch Display

`/finance/add` must automatically display the submitting user's current active share batch when one exists.

The active display must show:

- total files
- queued files
- processing files
- completed or auto-confirmed files
- review-required files
- duplicate files
- failed files
- cleanup state when applicable
- per-file status

The user may navigate away from the batch display without stopping queued processing.

Only one user's own active batch may be returned to that user. The active-batch API must never reveal another user's filenames, counts, statuses, intake IDs, or results.

### FR-008 Transient Batch Lifecycle

A batch begins only after confirmed files have been uploaded and durably queued.

A batch remains active while any item is:

- queued
- processing its first attempt
- processing its second attempt
- waiting for terminal finalization
- waiting for terminal storage cleanup

A batch reaches terminal state when every item is one of:

- auto-confirmed
- review required
- duplicate
- failed

After terminal Finance results are durable:

1. Delete every temporary image in the batch.
2. Complete or remove remaining queue messages.
3. Delete transient batch-item state.
4. Delete the transient batch.

No completed batch history is retained.

Durable Finance intake, candidate, transaction, duplicate, and failed-intake records remain governed by the existing Finance retention contract.

### FR-009 Serial Queue Processing

The queue consumer must process one image at a time on the Render Free service.

Requirements:

- one queue message maps to one image
- one image maps to at most one active candidate
- one Render instance performs at most one OCR operation at a time
- no unbounded in-memory backlog
- queued messages remain durable if the PWA closes
- interrupted messages become eligible for safe recovery
- a failed item does not block later items
- item processing order must not affect the final Finance result

The background consumer may continue through the batch until no immediately available messages remain. A recovery wake mechanism must handle queued or stale items if Render stops before the queue is drained.

### FR-010 Processing Attempts

Each image receives at most two total processing attempts.

Attempt behavior:

1. Run the first attempt.
2. If it fails for a recoverable OCR, download, transient Render, or transient persistence reason, start the second attempt immediately.
3. If the second attempt fails, persist a terminal failed Finance intake.
4. Continue processing the remaining batch items.

Validation rejection, missing authorization, and exact-image duplicate outcomes are terminal decisions and must not consume an unnecessary retry.

Retries must:

- preserve the same batch item and Finance intake lineage
- increment the existing processing-attempt count
- use idempotent finalization
- never create a second candidate or transaction
- respect the existing processing lease and fencing-token safeguards

If Render terminates between attempts, durable queue visibility and the recovery wake must allow the remaining permitted attempt to resume safely.

### FR-011 Temporary Image Lifecycle

Before confirmation:

- files remain in browser memory only
- no server cleanup is required when the user abandons the page

After durable handoff:

- files remain private in temporary Storage
- files are available only to the authorized processing path
- files are not displayed in Finance review
- files remain only until the entire batch is terminal

At batch completion:

- delete successful images
- delete review-required images
- delete duplicate batch objects when one was uploaded before the hash decision
- delete failed images
- verify deletion before removing transient batch state

Cleanup failures must remain visible to an authorized recovery process and retry without restoring user-facing batch history after cleanup succeeds.

### FR-012 Existing Finance OCR Pipeline

Every non-duplicate queued image must use the existing Finance pipeline:

```txt
validate image
-> compute per-user image hash
-> begin or recover Finance intake
-> run Tesseract OCR
-> normalize OCR text
-> parse exactly one transaction candidate
-> infer source
-> apply active Finance rules
-> assess transaction duplicates
-> evaluate auto-confirmation
-> finalize intake, candidate, and optional transaction
```

This feature must not create a second parser, rule engine, duplicate implementation, or confirmation implementation.

### FR-013 Auto-Confirmation

A shared-image candidate may auto-confirm only when:

- OCR and parsing complete successfully
- overall candidate confidence is at least `0.90`
- every field required by the existing Finance confirmation contract is present
- a sufficiently strong active Finance rule supports the decision
- source, category, direction, amount, and transaction date satisfy the existing Finance rules
- no exact-image duplicate exists
- no possible or strong transaction duplicate requires review
- no blocking validation warning exists
- the existing transactional duplicate recheck passes

Confidence of `0.90` alone is never sufficient.

Candidates that do not satisfy every safeguard must enter the existing Finance review flow.

### FR-014 Exact Image Duplicates

Exact-image duplicate detection must reuse the existing per-user image hash.

When an exact duplicate is found:

- do not run OCR again
- do not create another candidate
- do not create another transaction
- mark the transient batch item as duplicate
- tell the user that the image is a duplicate while the active batch is visible
- link to or identify the existing Finance result when the existing contract permits
- continue processing the remaining items

Duplicate matching must remain user-scoped. One user's image hash must never reveal whether another user submitted the same bytes.

### FR-015 Existing Finance Review

This feature must not create a separate batch review queue.

Candidates requiring human review must appear in the existing `/finance/review` experience and preserve its current:

- user ownership
- extracted text display
- extracted field display
- correction controls
- duplicate-resolution behavior
- confirmation safeguards
- correction-history behavior
- rule-learning behavior

Original image bytes are not available in review.

### FR-016 Failed Intake Review

After two failed attempts, the system must:

- persist the Finance intake with `failed` status
- retain its sanitized filename
- retain safe failure code, stage, and user-readable message
- retain the attempt count
- retain any safe extracted text or fields produced before terminal failure
- expose the failed intake in the existing Finance review page
- tell the user that the image was not processed successfully
- allow the user to use the existing Finance entry path or share the image again

The failed intake must remain visible after the transient batch and temporary image are deleted.

A failed intake without a candidate must not be silently omitted merely because the existing review query previously returned candidate rows only.

### FR-017 Background Wake and Recovery

Creating queue messages must trigger a best-effort authenticated wake of the Render consumer.

The system must also provide a free-tier-compatible recovery mechanism for:

- messages still queued after an interrupted Render process
- expired processing leases
- batch items whose first attempt ended without a terminal result
- terminal batches waiting for image cleanup

The queue and durable Finance state are authoritative. A wake request is only a processing signal and must not be treated as proof that work completed.

Recovery must be idempotent and must not exceed the two-attempt product limit.

### FR-018 No Notifications

The feature must not add:

- PWA push notifications
- email notifications
- SMS notifications
- a new in-app notification center

When the user returns:

- `/finance/add` shows an active batch if it still exists
- auto-confirmed transactions appear through the existing transaction experience
- review candidates appear through the existing Finance review experience
- failed intake items appear through the existing Finance review experience

### FR-019 No Batch History

The product must not provide a completed-batch list or batch detail history.

Batch identifiers may appear temporarily for processing, support, safe logging, and idempotency. After terminal cleanup, the batch and its transient item records are removed.

Long-lived Finance records must not require their transient batch record to remain valid.

### FR-020 Ordinary Finance Intake Compatibility

The existing `/finance/add` manual entry and ordinary screenshot entry must continue to work.

Opening `/finance/add` without a shared payload must retain its existing behavior except that an active shared batch is shown when one exists.

The new background flow must not require the existing direct single-image Render route to use Storage or Queues.

## Processing Flow

### Authenticated Share Flow

```txt
User selects 1-10 images in Android
-> User shares to installed IdeaDump PWA
-> Service worker receives multipart POST
-> PWA verifies session and Finance access
-> Files remain in browser memory
-> /finance/add shows confirmation list
-> User removes unwanted images
-> User confirms processing
-> PWA uploads accepted files to private temporary Storage
-> Server creates transient batch and one durable queue message per image
-> UI confirms that the user may close the PWA
-> Render wakes and claims one queue message
-> Render processes one image through the existing Finance pipeline
-> Result becomes auto-confirmed, review required, duplicate, or failed
-> Render continues serially with the next item
-> All items become terminal
-> System deletes every temporary batch image
-> System removes transient queue and batch state
```

### Signed-Out Share Flow

```txt
User shares images to IdeaDump
-> PWA finds no active authenticated session
-> PWA discards every in-memory image
-> PWA opens sign-in with a reshare explanation
-> User signs in
-> User returns to the source application and shares the images again
```

### Per-Image Decision Flow

```txt
Queued image
-> Validate and hash
-> Exact image duplicate?
   -> Yes: report duplicate, skip OCR, continue batch
   -> No: run Finance OCR pipeline
-> Recoverable failure?
   -> First failure: retry immediately
   -> Second failure: create failed intake for existing review
-> Candidate created
-> Confidence >= 0.90 and all Finance safeguards pass?
   -> Yes: auto-confirm through existing transactional contract
   -> No: send candidate to existing Finance review
```

## Logical Data Model

Executable forward migrations remain the schema source of truth. The exact table and column names may be refined during implementation, but the ownership, lifecycle, and retention behavior in this section are required.

### Transient Share Batch

```sql
finance_share_batches
---------------------
id uuid primary key
user_id uuid not null
status text not null
total_files integer not null
queued_files integer not null
processing_files integer not null
completed_files integer not null
review_files integer not null
duplicate_files integer not null
failed_files integer not null
created_at timestamptz not null
updated_at timestamptz not null
```

Requirements:

- user-owned
- maximum ten items
- present only during queued processing and cleanup
- deleted after terminal image cleanup
- never required by durable Finance rows after deletion

### Transient Share Batch Item

```sql
finance_share_batch_items
-------------------------
id uuid primary key
batch_id uuid not null
user_id uuid not null
intake_item_id uuid
storage_path text not null
original_filename text
mime_type text not null
file_size bigint not null
status text not null
attempt_count integer not null
failure_code text
failure_stage text
created_at timestamptz not null
updated_at timestamptz not null
```

Requirements:

- exactly one item per accepted shared image
- server-generated storage path
- one associated queue message at a time
- at most two processing attempts
- deleted with the transient batch after object cleanup

### Queue Message

Conceptual payload:

```json
{
  "batchId": "batch_uuid",
  "batchItemId": "batch_item_uuid",
  "processingVersion": 1
}
```

The consumer must derive and verify the batch owner, intake lineage, storage path, attempt count, and authorization from authoritative server-side data.

### Existing Finance Intake

`finance_intake_items` remains the durable per-image processing record.

The enhancement must reuse its current:

- user ownership
- screenshot source
- status model
- image hash
- sanitized original filename
- OCR text and confidence
- processing lease
- fencing token or attempt identifier
- processing attempt count
- failure code and stage
- processed timestamp

Failed shared images remain discoverable by the existing Finance review API after their transient batch is deleted.

### Existing Candidate and Transaction Records

The feature continues using:

- `finance_candidate_transactions`
- `finance_transactions`
- existing Finance rules, sources, categories, corrections, and duplicate fields

No batch-specific candidate or ledger schema may become a parallel source of truth.

## Security Requirements

- Require a valid authenticated user and current Finance module access before any confirmed image upload.
- Discard signed-out shares and require resharing after login.
- Never persist unconfirmed images.
- Treat every shared file, filename, MIME type, extension, and metadata field as untrusted.
- Revalidate every image on Render even if the browser or Next.js already validated it.
- Use a private Supabase Storage bucket.
- Generate storage paths server-side.
- Enforce user ownership in every batch and Storage operation.
- Keep new server-only tables and functions outside unnecessary browser exposure.
- If any new table is exposed through the Data API, grant access explicitly and enable ownership-based RLS.
- Never rely on `TO authenticated` without a user-ownership predicate.
- Never use editable user metadata for Finance authorization.
- Never expose Supabase service-role keys, secret keys, Render secrets, or unrestricted queue access to the browser.
- Keep queue messages free of image bytes, OCR text, access tokens, and signed URLs.
- Render must derive ownership from authoritative batch data and verified server credentials.
- Validate that the claimed storage object belongs to the claimed batch item and user.
- Preserve `PRD_008` rate limiting, image limits, safe logs, and Finance finalization protections.
- Do not include screenshot bytes or full sensitive OCR text in logs.
- Make duplicate hashes user-scoped.
- Make queue consumption and finalization idempotent.
- Delete temporary objects before deleting the only cleanup-tracking records.

---

## Reliability Requirements

- Queue creation must be durable before the safe-to-close UI appears.
- One failed item must not fail the remaining batch.
- The Render consumer must process serially.
- A recoverable first failure receives one immediate retry.
- No item receives more than two total attempts.
- Queue redelivery must preserve the same intake lineage.
- Processing leases and fencing tokens must prevent late attempts from overwriting terminal results.
- Finalization must not create duplicate candidates or transactions.
- Exact-image duplicate detection must skip redundant OCR.
- A Render restart must not lose confirmed queued work.
- A browser closure after durable handoff must not cancel queued work.
- A browser closure before durable handoff may interrupt submission and must never be represented as successful background processing.
- Recovery wakes must resume queued or stale work without requiring a paid always-on worker.
- Terminal cleanup must be retryable and idempotent.
- A batch must not be deleted until every temporary object has been deleted or is tracked for authorized cleanup recovery.

---

## Performance Requirements

- The confirmation list should appear promptly after the PWA receives the Android share.
- Client-side list rendering must support ten accepted images without freezing the page.
- The UI must show upload and durable-handoff progress after confirmation.
- The UI must not promise that the PWA may close while uploads or queue creation remain incomplete.
- Render OCR concurrency remains one.
- Files are processed serially without requiring the user to remain on `/finance/add`.
- Cold-start messaging must remain truthful and must not imply that Render is already processing merely because the work is durably queued.
- Active-batch status should update without a full application reload while the page is open.
- Polling or another free-tier-compatible status mechanism must be bounded and must stop after the batch disappears.

No end-to-end completion-time promise is made because batch duration depends on file count, Render cold starts, OCR duration, and free-tier capacity.

---

## Failure Behavior

| Failure | Required behavior |
| --- | --- |
| User is signed out | Discard in-memory files, open sign-in, and require resharing. |
| User lacks Finance access | Discard files and show access denied. |
| More than ten images are shared | Identify the limit and require removal until no more than ten processable images remain. |
| A file exceeds 4 MB | Mark that file invalid; do not upload it. |
| A file has an unsupported or misleading format | Mark that file invalid; do not upload it. |
| User closes before confirmation | Lose the in-memory selection; no server cleanup is required. |
| User closes during upload or queue creation | Do not claim durable handoff; recover or clean partial server state safely. |
| Some confirmed object uploads fail | Do not show the safe-to-close result until the accepted batch has a consistent durable handoff. |
| Render is cold | Keep work durable in the queue and wake Render; show truthful queued status. |
| Render stops mid-batch | Queue visibility and the recovery wake resume remaining eligible work. |
| First recoverable item attempt fails | Retry the same item immediately. |
| Second item attempt fails | Persist a failed intake, continue the batch, and show the failed intake in Finance review. |
| Exact image hash already exists for the user | Mark the item duplicate, skip OCR, identify the existing result when possible, and continue. |
| Candidate confidence is below `0.90` | Send it to existing Finance review. |
| Candidate confidence is at least `0.90` but a safeguard fails | Send it to existing Finance review. |
| Temporary image deletion fails | Retain authorized cleanup state and retry cleanup; do not expose the object publicly. |
| Free-tier capacity is unavailable | Keep durable queued state where possible, fail visibly when terminal, and never upgrade automatically. |

## Free-Tier Constraints

The feature must remain compatible with:

- the existing Vercel Hobby application
- the existing Supabase Free project
- the Render Free Finance OCR web service

The feature must not require:

- a paid Render background worker
- a paid queue
- a paid cache
- persistent Render disk
- a paid OCR API
- an automatic provider-plan upgrade

Temporary Storage objects and queue messages consume existing Supabase project capacity. Queue, Storage, database, bandwidth, and Render allowances must be reverified before production rollout.

The Render web service remains the OCR compute host. The durable queue and recovery wake compensate for browser closure and Render interruption; they do not convert Render Free into an always-on worker.

## Acceptance Criteria

### Share Target

- The installed PWA appears as an Android share target for PNG, JPEG, and WebP images.
- One supported image can be shared.
- Up to ten supported images can be shared in one action.
- Shared files open `/finance/add` in confirmation mode.

### Authentication

- Signed-out shares are discarded.
- Signed-out users are asked to sign in and then reshare.
- No anonymous batch, object, queue, or Finance record is created.
- Users without Finance access cannot upload or process shared images.

### Confirmation

- Shared images are not stored before confirmation.
- The confirmation page lists the received files.
- The user can remove individual files.
- OCR does not begin before confirmation.
- Invalid files are identified individually.

### Durable Background Handoff

- Confirmed images are uploaded to private temporary Storage.
- One durable queue message exists for every accepted image.
- The UI tells the user that the PWA may close only after the complete handoff succeeds.
- Closing the PWA after that message does not cancel the batch.
- Reopening `/finance/add` shows the active batch automatically.

### Processing

- Render processes no more than one image at a time.
- Each image produces no more than one candidate.
- A failed or duplicate image does not stop other images.
- A recoverable first failure retries immediately.
- No image receives more than two total attempts.
- Terminal failures create failed Finance intake items.

### Finance Decisions

- Auto-confirmation requires confidence of at least `0.90`.
- Auto-confirmation also requires all existing Finance safeguards.
- Candidates failing any safeguard enter existing Finance review.
- Exact duplicate images are detected by the existing per-user image hash.
- Exact duplicate images skip OCR and do not create duplicate candidates or transactions.

### Review

- Review-required candidates appear in the existing Finance review page.
- Failed intake items appear in the existing Finance review page.
- Only the submitting user can access those records.
- Review shows extracted text and fields where available.
- Review does not depend on the original image.

### Cleanup

- Every temporary image is deleted after all batch items are terminal.
- Failed images are deleted with the rest of the batch.
- Transient batch and batch-item state is deleted after verified object cleanup.
- No completed batch history remains.
- Durable transactions, candidates, reviews, duplicates, and failed intakes remain accessible through existing Finance behavior.

### Security and Cost

- Storage is private and user-scoped.
- Queue messages contain opaque identifiers only.
- No privileged credential reaches the browser.
- Cross-user batch, Storage, intake, candidate, transaction, and review access is denied.
- The feature requires no paid worker, queue, cache, disk, or OCR provider.
