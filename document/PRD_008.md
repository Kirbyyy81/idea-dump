# Proposal: Free-Tier Asynchronous Finance OCR

## Document Status

| Field | Value |
| --- | --- |
| Status | Proposal for product and architecture review |
| Module | Finance |
| Primary capability | Asynchronous screenshot OCR |
| Cost constraint | All components must remain within free-tier allowances |
| Proposed OCR host | Render Free web service |
| Durable platform | Supabase Free |
| Application host | Existing Vercel Hobby deployment |
| Implementation approval | Not granted by this document |

This PRD proposes moving Tesseract OCR out of the synchronous Finance upload request and into a free Render web service. It records the expected behavior, limitations, security requirements, failure handling, and decisions that must be confirmed before implementation.

The proposal intentionally uses a **Render Free web service**, not a Render background worker. Render background workers are not available as Free instances. This distinction is central to the design and its limitations.

---

## Executive Summary

The current Finance screenshot flow performs upload validation, Tesseract OCR, parsing, duplicate assessment, rule evaluation, candidate creation, and Supabase writes before returning a response to the browser. The user sees only a loading state while the entire synchronous request runs.

Recent live processing data showed one successful request spending approximately:

| Stage | Observed duration |
| --- | ---: |
| OCR | 3.28 seconds |
| Parsing and database work | 0.46 seconds |
| Finalization | 0.07 seconds |
| Recorded server total | 3.80 seconds |

The latest observed incomplete attempts recorded `ocr_started` without `ocr_completed`, indicating failure or interruption during OCR or immediately afterward.

This proposal changes the user experience from “wait for processing” to “submit and monitor”:

1. The screenshot is uploaded to private temporary Supabase Storage.
2. A durable Finance intake and OCR job are created.
3. The app immediately returns a queued status.
4. Supabase sends a wake request to a Render Free web service.
5. Render claims the queued job and runs Tesseract.
6. Render writes the candidate, processing events, and final state to Supabase.
7. The UI observes status changes and opens the review workflow when ready.

This proposal improves perceived responsiveness and makes retry behavior explicit. It does **not** guarantee faster OCR. Render Free has weak CPU allocation and cold starts, so end-to-end processing may take longer than the current server route, especially after idle periods.

---

## Product Constraint

The authoritative constraint for this proposal is:

> The OCR workflow must not require a paid hosting plan, paid background worker, paid queue, paid cache, persistent disk, or paid OCR API.

The system may use free-tier quotas from the existing providers, but it must not silently upgrade, enable metered paid resources, or depend on a trial that later converts to a paid service.

Free-tier availability and quotas are external platform policies and may change. Before implementation and before every production rollout, the current limits must be reverified against official provider documentation.

---

## Problem Statement

The current synchronous upload flow has four product and reliability problems:

- The browser waits for the complete OCR pipeline before receiving useful feedback.
- Every request creates and terminates a new Tesseract worker.
- OCR failures are difficult for the user to distinguish from a slow request.
- A request interruption can leave an intake without a complete processing trail.

The user should be able to submit a screenshot, leave the page, and later review the extracted transaction without keeping a long-running browser request open.

---

## Goals

- Return a durable queued state shortly after upload.
- Run Tesseract outside the browser or mobile device.
- Use Render Free as the proposed Tesseract runtime.
- Keep Supabase as the source of truth for jobs, status, OCR output, candidates, and transactions.
- Keep Vercel responsible for the Next.js application and user-facing APIs.
- Preserve the existing deterministic parser, source detection, rules, duplicate assessment, and review behavior.
- Support retries without creating duplicate candidates or transactions.
- Make queued, processing, review, completed, failed, and retry states visible to the user.
- Keep screenshot storage private and temporary.
- Stay within free-tier allowances without paid supporting services.

---

## Non-Goals

- Guaranteed immediate OCR after a long idle period.
- A paid Render background worker.
- Render Key Value, Redis, or another paid queue.
- A persistent Render disk.
- A paid OCR provider.
- OCR on the user's phone or browser.
- Permanent screenshot archiving.
- Horizontal worker scaling in the initial proposal.
- More than one transaction candidate per screenshot.
- Changing the existing Finance confirmation, duplicate, category, or learning-rule product policies.
- Moving ordinary Finance CRUD routes, authentication, dashboards, or review APIs to Render.

## Current Architecture

The current flow is synchronous:

```text
Browser
  -> Next.js POST /api/finance/upload
  -> validate and buffer image
  -> begin Supabase intake
  -> create Tesseract worker
  -> run OCR
  -> terminate Tesseract worker
  -> normalize and parse text
  -> load sources, rules, and categories
  -> assess duplicates
  -> create candidate
  -> update processing events
  -> return HTTP response
```

The browser waits at the upload screen until the final HTTP response. The current UI does not expose processing phases and does not automatically move the user to a newly prepared review item.

---

## Proposed Architecture

```text
Browser / PWA
  -> Next.js authenticated intake API
  -> private Supabase Storage upload
  -> atomic intake + queue operation
  -> immediate queued response

Supabase
  -> durable intake and queue message
  -> asynchronous authenticated wake request

Render Free web service
  -> verify wake request
  -> claim one queue message
  -> download and revalidate private image
  -> run Tesseract OCR
  -> normalize, parse, apply rules, assess duplicates
  -> create or update candidate idempotently
  -> update intake and processing events
  -> acknowledge queue message after success

Browser / PWA
  <- status through Supabase Realtime or polling
  -> Finance review page when ready
```

### Runtime Ownership

| Responsibility | Proposed owner |
| --- | --- |
| UI, upload initiation, review UI | Next.js on Vercel |
| User authentication and module access | Supabase Auth and Next.js |
| Temporary screenshot bytes | Private Supabase Storage |
| Intake state and processing history | Supabase Postgres |
| Durable queue | Supabase Queues or an approved equivalent in Supabase Postgres |
| Worker wake request | Supabase Database Webhook / `pg_net` |
| Tesseract OCR | Render Free web service |
| Parser, rules, duplicate assessment | Shared Finance processing library executed on Render |
| Candidate and ledger persistence | Existing Supabase tables and transactional RPCs |
| Progress delivery | Supabase Realtime or bounded polling |

### Why a Free Web Service

Render Free supports web services but not free background-worker instances. The proposed service therefore exposes a small authenticated wake endpoint and performs worker behavior inside a web-service process.

The service is not a general public Finance API. Its only public routes should be operational routes such as:

```text
POST /internal/finance-ocr/wake
GET  /health
```

The wake endpoint must not accept user-supplied transaction data or arbitrary Storage paths. It should treat the request only as a signal, then claim the authoritative job from Supabase.

## Proposed User Experience

### Upload

After a valid screenshot is selected:

1. The app uploads it to private temporary Storage.
2. The app creates the intake and queues processing.
3. The app shows `Screenshot queued` without waiting for OCR.
4. The selected file is cleared only after the durable queue operation succeeds.

### Processing Status

The UI should show these user-facing states:

| Internal state | User-facing label | User action |
| --- | --- | --- |
| `uploading` | Uploading screenshot | Wait or cancel before intake creation |
| `queued` | Waiting to be processed | Leave page safely |
| `processing` | Reading screenshot | Leave page safely |
| `review` | Ready for review | Open candidate |
| `completed` | Transaction confirmed | Open transaction |
| `failed` | Screenshot could not be processed | Retry or remove |
| `duplicate` | Possible duplicate | Review duplicate evidence |

The app must not promise instant completion. After Render has been idle, the UI should explain that free processing may take approximately a minute or longer to start.

### Navigation

- The upload page should link to the review queue immediately after queuing.
- The Finance dashboard should display pending processing and review counts separately.
- Processing should continue when the user navigates away or closes the browser.
- A failed item should expose a retry action and a concise safe error message.

## Functional Requirements

### FR-001 Authenticated Intake

- Only an authenticated user with Finance module access may create an intake.
- The server must derive `user_id` from the verified session, never from request JSON.
- Intake creation, Storage ownership, and queue creation should be atomic where practical.

### FR-002 Private Temporary Upload

- Accept PNG, JPEG, or WebP only.
- Enforce the existing 4 MB maximum after any approved compression.
- Validate magic bytes, declared MIME type, dimensions, and decoded pixel limits.
- Store objects under an ownership-scoped path that cannot be selected by another user.
- Use a private bucket; no permanent public URL may exist.

### FR-003 Durable Queue

- A queue message should contain only an opaque intake identifier and processing version.
- It must not contain raw image bytes, OCR text, user secrets, or a client-provided `user_id`.
- Queue visibility must exceed the worst expected free-tier cold-start and OCR duration.
- A message is acknowledged only after durable success or an explicit terminal failure.

### FR-004 Render Wake Request

- An asynchronous Supabase Database Webhook or `pg_net` request should wake Render after a job is committed.
- The wake call must not block the user-facing intake transaction.
- A shared secret or equivalent service authentication must protect the endpoint.
- Secrets used by database networking must be stored in Supabase Vault, not hardcoded in a migration or webhook definition.
- The Render endpoint should return quickly after securely accepting the wake signal.

### FR-005 Worker Claim

- Render must atomically claim a visible job before processing it.
- Initial concurrency is exactly one OCR job per process.
- If multiple wake requests arrive, the service must not run the same job concurrently.
- The service may drain a small bounded number of queued jobs while it remains awake.

### FR-006 OCR Processing

- Tesseract should run in Node.js using the existing English model.
- The language model should be bundled with the deploy and version-pinned.
- A warm Render instance may reuse one initialized worker through a serialized worker pool.
- The system must recreate the worker safely after restart or recognition failure.
- Every OCR attempt must record start time, completion time, confidence, worker version, model version, and error stage.

### FR-007 Shared Finance Pipeline

The existing processing code should be extracted from the Next.js route into runtime-neutral modules so Render and local verification can reuse:

- image validation
- OCR normalization
- source detection from filename and OCR signals
- deterministic transaction parsing
- rule evaluation
- duplicate assessment
- candidate creation
- auto-confirm eligibility
- processing-event generation

Shared modules must not depend on `NextRequest`, `NextResponse`, React, browser APIs, or route-local session state.

### FR-008 Idempotency

- `image_hash` continues to prevent exact screenshot duplication.
- One intake may produce at most one active candidate.
- Replaying a queue message must update or recover the existing intake lineage rather than insert another candidate.
- Final confirmation must continue to use the transactional database operation and final duplicate recheck.
- A retry must not create a second ledger transaction.

### FR-009 Completion and Cleanup

On success:

- persist OCR, normalized text, source evidence, parser output, duplicate assessment, and candidate
- update intake to `review`, `completed`, or `duplicate`
- acknowledge the queue message
- remove the temporary Storage object according to the approved retention decision

On failure:

- record a safe error category and internal diagnostic detail separately
- increment the attempt count
- preserve the message for retry until the maximum attempt count
- mark the intake `failed` after retry exhaustion
- apply the approved failed-image retention policy

### FR-010 Retry and Recovery

- Users may retry failed jobs.
- A scheduled recovery wake may be proposed using Supabase Cron, but it must remain within free-tier allowances and must not be used solely to defeat Render's idle spin-down policy.
- Recovery should target queued or abandoned jobs, not continuously ping Render to keep it warm.
- Stale `processing` claims must become claimable again after their visibility window.

### FR-011 Progress Delivery

- Prefer Supabase Realtime when available within quota.
- Fall back to bounded polling with exponential backoff.
- The client must stop polling on terminal states and when the component unmounts.
- Progress subscriptions and queries must remain user-scoped through RLS.

## Security Requirements

### User and Storage Isolation

- Storage must remain private.
- Object policies must scope paths to the authenticated user's ID.
- An authenticated user must never be able to read another user's screenshot, job, candidate, or status.
- Render must re-fetch the authoritative intake and reject missing, terminal, or invalid lineage.

### Render Endpoint Security

- The wake endpoint is public at the network level because Render Free web services do not provide a private inbound network from Supabase.
- Require a high-entropy shared secret or signed request.
- Compare secrets using a timing-safe operation.
- Reject requests with an invalid content type, excessive body size, unknown schema, or stale timestamp if request signing is used.
- Apply rate limiting that does not require a paid cache.
- Never accept a Storage URL or database operation directly from the webhook payload.

### Supabase Credentials

- Prefer a dedicated modern Supabase secret key for the Render worker so it can be rotated independently.
- Keep the key only in Render environment secrets.
- Never expose it through `NEXT_PUBLIC_*`, the browser, logs, queue messages, or webhook bodies.
- Secret-key clients bypass RLS; every worker query must still scope operations by both `user_id` and `intake_id` or use narrowly defined server RPCs.

### Database Webhook Secrets

- Do not store worker secrets as plaintext in SQL source control.
- Store outbound webhook secrets in Supabase Vault.
- Log only request IDs and response status, never secret headers.

### Untrusted Image Handling

- Revalidate the object after Render downloads it.
- Enforce byte, dimension, and pixel limits before OCR.
- Reject polyglot or mismatched file content.
- Never execute metadata or OCR text.
- Treat filenames, OCR output, webhook payloads, and queue data as untrusted input.

## Free-Tier Limitations

### Render Free Web Service

Current official Render documentation states that free web services:

- receive 512 MB RAM and 0.1 CPU according to the current pricing table
- spin down after 15 minutes without inbound traffic
- may take about one minute to spin back up
- use an ephemeral filesystem
- may restart at any time
- do not support persistent disks
- cannot scale beyond a single instance
- do not support shell or SSH access
- share a monthly free-instance-hour allowance at the workspace level
- may be suspended for unusually high service-initiated external traffic

Implications:

- OCR after an idle period can be substantially slower than current local processing.
- The Tesseract worker and language model must be reinitialized after cold starts.
- No correctness may depend on in-memory state or local files.
- Only one OCR job should run at a time until memory and CPU measurements prove otherwise.
- A deploy or platform restart may interrupt an active job.
- The durable queue and idempotent database contract are mandatory, not optional enhancements.

### Supabase Free

The proposal consumes free-tier database, Storage, Realtime, Database Webhook / `pg_net`, and queue capacity. Exact quotas can change and must be checked before rollout.

Implications:

- Temporary images require lifecycle cleanup.
- Realtime connections and polling must be bounded.
- Queue messages and processing events require retention or pruning rules.
- Webhook failures must be observable through `net` response history and application events.
- Database size must be monitored because OCR text, events, and queue archives accumulate.

### Vercel Hobby

The existing application remains subject to Hobby usage caps and personal/non-commercial eligibility.

Implications:

- Direct browser-to-Supabase upload is preferred to avoid routing image bytes through Vercel twice.
- User-facing Next.js functions should remain short and should not wait for Render.
- The design must not require paid Vercel background execution or paid queue products.

### Free-Tier Policy Risk

Free tiers are not service-level agreements. Providers may change quotas, suspend inactive services, or discontinue features. This proposal accepts that risk in exchange for zero recurring infrastructure cost.

If free limits become insufficient, the system should degrade visibly to manual entry and retry rather than incur charges automatically.

## Consideration Factors

### Latency

| Scenario | Expected behavior |
| --- | --- |
| Render warm | OCR begins shortly after queue wake |
| Render cold | Start can be delayed by approximately one minute, then OCR runs on limited CPU |
| Wake webhook fails | Job remains queued until manual retry or scheduled recovery |
| Render restarts mid-job | Queue visibility expires and a later attempt reclaims the job |

The proposal optimizes browser responsiveness, not guaranteed OCR completion time.

### CPU and Memory

- Current samples are roughly phone-screenshot sized and previously completed OCR within several seconds on the existing runtime.
- Render Free CPU is materially weaker and must be benchmarked.
- Images should be resized or compressed before OCR when dimensions exceed an approved threshold.
- The existing 25-million-pixel server limit may be too high for Render Free and should be reviewed.
- Concurrency begins at one.

### Reliability

- Database state and queue visibility are authoritative.
- In-memory queues are prohibited.
- Every step must be repeatable.
- A processing attempt should have a maximum duration and heartbeat.
- An abandoned claim must recover without administrator SQL.

### Privacy

- Async processing requires temporary image retention, unlike the current immediate in-memory flow.
- Screenshots can contain account names, recipient names, balances, reference IDs, and transaction history.
- The shortest practical retention period is preferred.
- A future setting for permanent screenshot evidence is outside this proposal.

### Maintainability

- OCR and parsing code should stay in the existing repository.
- Runtime-neutral Finance modules prevent logic drift between Vercel, Render, and local verification.
- Render configuration should be declarative and reviewable, such as a `render.yaml` proposal or documented dashboard settings.
- Dependencies and the Node runtime must be pinned.

### Cost Protection

- No paid Render background worker.
- No Render persistent disk.
- No Render Key Value.
- No paid OCR API.
- No automatic paid upgrades.
- No artificial keep-alive traffic intended to bypass free-service sleep behavior.
- Monitor all provider quota dashboards and document manual fallback behavior.

## Failure Modes and Required Responses

| Failure | Required response |
| --- | --- |
| Storage upload fails | Do not enqueue; show upload error |
| Queue transaction fails | Preserve or clean uploaded object; show retryable error |
| Wake webhook fails | Leave durable job queued; record wake failure |
| Render cold-start timeout | Leave job queued; show delayed state |
| Render restarts | Let queue visibility expire and retry idempotently |
| Tesseract initializes unsuccessfully | Record OCR initialization failure and retry within policy |
| OCR finds no readable text | Mark terminal unreadable failure; allow user retry or manual entry |
| Parser cannot confirm fields | Create review candidate with available OCR evidence |
| Supabase write fails after OCR | Do not acknowledge message; retry safely |
| Candidate already exists | Recover existing lineage instead of inserting another candidate |
| Storage cleanup fails | Record cleanup event and retry cleanup separately |
| Free quota exhausted | Stop processing, show service-unavailable/manual-entry guidance, never incur charges automatically |

## Observability

The system should expose enough data to answer:

- How long did upload, queue wait, cold start, worker initialization, OCR, parsing, and persistence take?
- Which stage failed?
- How many attempts occurred?
- Is the Render worker warm, cold, or unavailable?
- How many messages are queued, processing, failed, or abandoned?
- Did screenshot cleanup succeed?

Minimum metrics:

- queue depth
- oldest queued age
- processing success rate
- OCR duration percentiles
- cold-start count
- retry count
- terminal failure count by stage
- orphaned Storage object count
- free-tier usage indicators where provider APIs expose them

Render Free lacks private worker health monitoring, so application-level processing events and a bounded heartbeat are required. The heartbeat must not be implemented as keep-alive traffic.

## Rollout Proposal

### Phase 0: Benchmark

- Deploy an isolated Render Free proof of concept.
- Run the two existing Ryt Bank screenshots and additional representative sizes.
- Record cold-start, Tesseract initialization, OCR duration, memory, and total duration.
- Confirm a 512 MB instance can process the accepted image limits reliably.
- Do not connect the proof of concept to production Finance writes.

### Phase 1: Shared Processing Library

- Extract runtime-neutral image validation and Finance processing logic.
- Keep the current synchronous route functioning.
- Verify parser and duplicate results remain identical.

### Phase 2: Durable Intake and Temporary Storage

- Add the private temporary bucket and ownership policies.
- Add durable queued state and idempotent claim behavior.
- Keep Render disabled behind a feature flag.

### Phase 3: Render Free Pilot

- Enable the flow for the owner account only.
- Keep manual entry and the synchronous fallback available.
- Validate wake, retry, cleanup, and review behavior.

### Phase 4: General Finance Rollout

- Enable for users with Finance module access.
- Retain the ability to disable asynchronous OCR globally.
- Monitor quota and queue age.

## Acceptance Criteria

- Upload returns a queued state without waiting for OCR completion.
- The user may leave the upload page while processing continues.
- A warm Render instance can process an accepted representative screenshot.
- A cold Render instance eventually processes a durable queued job or exposes a retryable failure.
- No paid Render service or add-on is required.
- No paid OCR provider is required.
- Original screenshots are private and removed according to the approved retention policy.
- Every database and Storage operation is user-scoped or executed through a narrow verified server contract.
- Replayed jobs do not create duplicate candidates or transactions.
- Failed and abandoned jobs can be retried without administrator intervention.
- The UI distinguishes queued, processing, review, completed, duplicate, and failed states.
- Free-tier exhaustion fails closed and never creates automatic charges.
- Existing Finance parser, source detection, rules, duplicate assessment, and confirmation behavior remain unchanged.

## Product and Architecture Decisions Requiring Approval

This proposal does not assume approval of the following decisions:

1. **Temporary image retention:** delete immediately after successful OCR, retain failures for a short troubleshooting window, or delete all terminal images immediately.
2. **Failed-image retention duration:** proposed options are immediate deletion, 1 hour, or 24 hours.
3. **Cold-start UX:** whether the UI should state that free processing may take a minute or longer.
4. **Fallback:** whether a failed Render job may be processed synchronously by the existing Vercel route or must fall back only to manual entry.
5. **Image dimensions:** the maximum decoded pixel count suitable for 512 MB RAM and limited CPU.
6. **Retry policy:** maximum attempts, visibility timeout, and delay between attempts.
7. **Recovery wake:** manual retry only or a low-frequency Supabase Cron recovery call.
8. **Realtime versus polling:** preferred progress transport and fallback interval.
9. **Auto-confirmation:** whether an asynchronously processed candidate may retain the existing automatic-confirmation behavior.
10. **Render configuration:** native Node runtime or Docker. Native Node is the initial recommendation unless reproducible OS-level dependencies require Docker.

No implementation should begin until these decisions are reviewed with the product owner.

## Alternatives Considered

### Keep Synchronous Vercel OCR

Advantages:

- simplest architecture
- no temporary image storage
- current successful processing is relatively fast

Disadvantages:

- browser blocks until completion
- request failures remain coupled to OCR
- worker initialization happens per request

### Supabase Edge Function Runs Tesseract

Rejected for this proposal because hosted Edge Functions have strict CPU and memory limits and do not support some worker or multithreading patterns used by CPU-heavy Node libraries. Background execution does not remove those resource limits.

### Paid Render Background Worker

Operationally preferable but rejected by the zero-cost constraint.

### External OCR Provider

Potentially faster and more accurate but rejected because free quotas may be temporary, require billing setup, or lead to paid usage.

### Browser Tesseract

Rejected because it consumes user CPU, memory, battery, and data and creates inconsistent behavior across phones.
