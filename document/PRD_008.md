# Proposal: Free-Tier Direct Finance OCR on Render

## Document Status

| Field | Value |
| --- | --- |
| Status | Revised proposal for product and architecture review |
| Module | Finance |
| Current-phase capability | Direct synchronous screenshot OCR on Render |
| Future reliability phase | Optional Supabase Storage and Queue workflow |
| Cost constraint | All components must remain within free-tier allowances |
| OCR host | Render Free web service |
| Durable data platform | Existing Supabase Free project |
| Application host | Existing Vercel Hobby deployment |
| Implementation approval | Not granted by this document |
| External limits reviewed | 15 July 2026 |

This revision records the selected sequencing for Finance OCR:

1. Move OCR from the Next.js upload route to a Render Free web service.
2. In the current phase, upload directly from the browser to Render and wait for the review result.
3. Keep screenshot bytes only in browser and Render memory.
4. Defer Supabase Storage, Supabase Queues, asynchronous processing, and automatic retry to a future reliability phase.

The current phase deliberately favors a smaller architecture. The requested sequencing confirms the corresponding product trade-off: the user waits synchronously, and a failed or interrupted request can require the screenshot to be uploaded again. The future phase remains available if product usage demonstrates that durable retry is worth the additional Storage, queue, cleanup, wake, and status-management complexity.

The Render runtime must be a **Free web service**, not a Render background worker. Free background-worker instances are not available.

---

## Executive Summary

The current Finance screenshot route buffers an image inside Next.js, creates a Tesseract worker, performs OCR, normalizes and parses the text, checks rules and duplicates, writes Finance records to Supabase, and only then responds to the browser.

Recent live processing data showed one successful request spending approximately:

| Stage | Observed duration |
| --- | ---: |
| OCR | 3.28 seconds |
| Parsing and database work | 0.46 seconds |
| Finalization | 0.07 seconds |
| Recorded server total | 3.80 seconds |

Moving this work to Render relocates CPU and request-duration pressure away from Next.js and avoids transferring the image through Vercel. It does **not** inherently make OCR faster. Render Free has limited CPU and cold starts, so it may be slower than the present measurement.

The proposed current-phase flow is:

1. The signed-in browser selects a screenshot.
2. The browser obtains its current Supabase access token.
3. The browser sends the screenshot and original filename directly to Render as `multipart/form-data`, with `Authorization: Bearer <access-token>`.
4. Render validates the access token and Finance module access, derives the user identity from the verified token, and never trusts a body-supplied `user_id`.
5. Render validates the image, computes its hash, acquires or recovers a short processing lease for the intake, runs Tesseract and the existing Finance processing pipeline, and finalizes the candidate, events, and optional confirmed transaction in Supabase.
6. Render returns the existing upload response shape to the browser and discards the screenshot bytes.

The user remains on the request while upload, OCR, and persistence complete. The UI should show meaningful phases such as `Uploading`, `Reading screenshot`, and `Preparing review` instead of a single generic loading state.

## Product Constraint

The authoritative cost constraint is:

> The OCR workflow must not require a paid hosting plan, paid background worker, paid queue, paid cache, persistent disk, or paid OCR API.

The application may use existing provider free tiers, but it must not silently enable metered infrastructure or depend on a trial that later becomes paid. Free-tier limits and workspace billing state must be reverified before every production rollout. Render outbound-bandwidth overage can be billed when a payment method exists, and a pipeline-minute spend limit must not be assumed to cap bandwidth charges.

## Problem Statement

The current implementation has four problems:

- OCR runs inside the Next.js request and consumes Vercel-side CPU and duration.
- The browser transfers the image through Next.js even though the image is not retained there.
- Every request creates and terminates a Tesseract worker with caching disabled.
- The UI exposes only a generic wait and does not distinguish upload, OCR, and review preparation.

The current phase should move the expensive work to Render without introducing durable screenshot storage or a queue before product usage proves they are necessary.

---

## Current-Phase Goals

- Upload screenshots directly from the browser to Render.
- Keep Next.js out of the image transfer and OCR execution path.
- Authenticate every OCR and warm-up request.
- Preserve Finance module authorization and user ownership.
- Retain screenshot bytes in memory only and discard them after the request.
- Preserve the existing deterministic parser, normalization, rules, duplicate assessment, and candidate review behavior unless a requirement below explicitly tightens it. Whether auto-confirmation remains enabled during the pilot is still an open decision.
- Preserve the existing successful response shape used by the Finance add page.
- Reuse one lazily initialized Tesseract worker on a warm Render instance.
- Serialize or tightly bound OCR concurrency for a 512 MB, 0.1 CPU instance.
- Provide honest, useful synchronous progress states.
- Remain within free-tier limits.

---

## Current-Phase Non-Goals

- Durable screenshot retry after browser disconnect or Render restart.
- Allowing the user to close the browser while guaranteeing that OCR will finish.
- Supabase Storage for Finance screenshots.
- Supabase Queues or another queue.
- Supabase Realtime or polling for background OCR status.
- A paid Render background worker.
- A persistent Render disk.
- Render Key Value, Redis, or another supporting cache service.
- A paid OCR provider.
- Browser-side Tesseract.
- More than one transaction candidate per screenshot.
- Moving ordinary Finance CRUD, dashboards, authentication pages, or review APIs to Render.
- Artificial keep-alive traffic intended to prevent Render Free from spinning down.

## Current Application Behavior

The current synchronous flow is:

```text
Browser
  -> Next.js POST /api/finance/upload
  -> authenticate user and check Finance access
  -> validate and buffer image
  -> compute image hash and begin intake
  -> create Tesseract worker with cache disabled
  -> run OCR
  -> terminate Tesseract worker
  -> normalize and parse text
  -> load sources, rules, and categories
  -> assess duplicates
  -> create candidate
  -> optionally auto-confirm
  -> update processing events and intake state
  -> return HTTP response
```

Current implementation facts:

- The browser sends multipart data to `app/api/finance/upload/route.ts`.
- The route enforces a 4 MB file limit and accepts PNG, JPEG, and WebP.
- The route checks declared MIME type, magic bytes, dimensions parsed from format headers, a 12,000-pixel width and height cap, and a 25-million-pixel total cap. It does not fully decode the image to validate those dimensions.
- The route buffers the image in memory and discards it after processing.
- Finance screenshots are not currently stored in Supabase Storage.
- Supabase stores metadata and derived data including image hash, filename, OCR text, source evidence, candidates, and processing events.
- `lib/finance/ocr.ts` creates and terminates a Tesseract worker for every request and uses `cacheMethod: 'none'`.
- The original filename is passed into source detection and can provide useful source evidence.
- The live Supabase schema currently denies authenticated clients direct access to Finance and RBAC tables. Existing Finance RPCs used by the route are executable by the server role, not by `authenticated` users.

The existing source detector can currently select a source from filename evidence alone. The revised requirement is stricter: a filename may suggest a source, but it must not be the only authoritative signal used to select that source.

## Proposed Current-Phase Architecture

```text
Browser / PWA
  -> obtain current Supabase access token
  -> POST screenshot and original filename directly to Render
  -> show synchronous progress phases

Render Free web service
  -> validate Origin and CORS policy
  -> validate Supabase access token
  -> verify Finance module access
  -> derive user ID from verified identity
  -> validate image and compute image hash
  -> acquire bounded OCR capacity
  -> begin or recover a short processing lease for the intake
  -> initialize or reuse Tesseract worker
  -> run OCR in memory
  -> normalize, parse, infer source, apply rules, assess duplicates
  -> atomically finalize events, candidate, intake, and optional transaction in Supabase
  -> return existing upload response shape
  -> discard screenshot bytes

Browser / PWA
  <- receive review or confirmed-transaction payload
  -> show success and open or link to the relevant review state
```

### Runtime Ownership

| Responsibility | Current-phase owner |
| --- | --- |
| Sign-in session and access-token refresh | Supabase Auth and browser client |
| UI, file selection, progress, and review navigation | Next.js application |
| Screenshot transfer | Browser directly to Render |
| Screenshot bytes during processing | Render memory only |
| Identity validation | Render against Supabase Auth |
| Finance module authorization | Render against authoritative RBAC data or a narrow authorization contract |
| Image validation and hashing | Render |
| Tesseract OCR | Render Free web service |
| Parser, source inference, rules, and duplicate assessment | Shared Finance processing library on Render |
| Durable Finance metadata and results | Supabase Postgres |
| Ordinary Finance APIs and pages | Existing Next.js application |

### Public Render Routes

The proposed service may expose only a small route surface:

```text
POST /v1/finance/ocr
POST /warm
GET  /health
```

The exact paths may be adjusted during implementation, but their responsibilities must remain separate:

- The OCR route accepts an authenticated screenshot request.
- `/warm` authenticates and authorizes the caller, then invokes the same Tesseract initialization promise used by OCR.
- `/health` reports process health only. It must not be described as an OCR warm-up unless it initializes the same worker.

## User Experience

### Synchronous Progress

The direct design remains a single upload, OCR, persistence, and response wait. The UI should expose these phases:

| Phase | User-facing label | Meaning |
| --- | --- | --- |
| `uploading` | Uploading screenshot | The browser is transferring the file to Render |
| `reading` | Reading screenshot | The upload is complete and Render is processing the request |
| `preparing` | Preparing review | The final response arrived and the browser is applying it or navigating |
| `completed` | Ready | A review candidate or confirmed transaction is available |

Use `XMLHttpRequest` or another progress-capable transport if actual upload progress is required; ordinary `fetch` does not expose upload progress events. After upload completion, show `Reading screenshot` until the final JSON response arrives, followed by the brief `Preparing review` transition while the browser applies the payload. Do not claim to distinguish OCR, parsing, and database sub-phases unless a separate streamed progress protocol is explicitly approved.

### Cold Starts

The UI must not promise instant processing. If Render has spun down, waking the service may take about one minute before OCR begins. The UI should explain this safely without implying that the screenshot has been durably queued.

### Failure Behavior

If the screenshot request fails before a durable result exists:

- retain the selected file in the page when the browser can still do so safely
- show a concise error and a retry action
- explain when the user must select the file again
- do not claim that background processing will continue

If the browser loses the response after Render has already persisted a result, a retry must use the image hash and intake lineage to recover or return the existing result instead of creating a duplicate candidate or transaction.

## Functional Requirements

### FR-001 Authenticated OCR Request

- Require `Authorization: Bearer <Supabase access token>`.
- Accept only Supabase user access tokens, never API keys or refresh tokens in the bearer header.
- Derive the user ID from the validated token.
- Never accept or trust a `user_id` supplied in multipart fields, JSON, query parameters, or filenames.
- Reject missing, malformed, expired, or invalid credentials with `401`.

### FR-002 Finance Module Authorization

- A valid Supabase login is necessary but not sufficient.
- Verify that the authenticated user currently has access to the Finance module.
- Reject authenticated users without Finance access with `403`.
- Do not use editable `user_metadata` for authorization.
- Authorization must use authoritative RBAC data or a narrowly defined server contract.

### FR-003 Direct Multipart Upload

- The browser sends the screenshot directly to Render as `multipart/form-data`.
- Preserve the sanitized original filename as source-detection evidence.
- Do not proxy the image through Next.js.
- Do not upload the image to Supabase Storage in the current phase.
- Enforce an overall request-size limit in addition to the file-size limit.

### FR-004 Image Validation

- Accept PNG, JPEG, and WebP only.
- Enforce a maximum file size of 4 MB.
- Validate declared MIME type against magic bytes.
- Fully decode the image, or use a parser proven to validate decoded dimensions safely, before OCR. Header-only dimensions are not sufficient evidence by themselves.
- Enforce maximum width, height, and total decoded pixels.
- Treat metadata, filenames, and OCR text as untrusted input.
- Benchmark the existing 25-million-pixel limit before retaining it on a 512 MB instance.

### FR-005 In-Memory Screenshot Lifecycle

- Keep the screenshot only in request memory.
- Do not write the screenshot to Render disk, logs, Supabase Storage, or another cache.
- Compute the image hash before OCR.
- Release all screenshot buffers after success or failure.
- Correctness must not depend on Render's ephemeral filesystem.

### FR-006 Reusable Tesseract Worker

- Initialize Tesseract lazily through a shared `ensureWorkerReady()` promise.
- Reuse one initialized worker while the Render process remains warm.
- Use the same initialization path from the OCR route and `/warm`.
- Serialize recognition with a mutex or equivalent bounded-capacity guard.
- Start with one active OCR operation per Render instance.
- Recreate the worker after initialization or recognition failure when safe.
- Bundle and version-pin the English model and runtime dependencies.
- Do not rely on runtime-downloaded cache files surviving a restart.

### FR-007 Overload Behavior

- Do not build an unbounded in-memory backlog.
- If OCR capacity is occupied, reject excess work with `429` or `503` and a useful `Retry-After` value.
- Rate-limit OCR and warm-up calls per verified user and, where useful, by network source.
- Rate limiting must not require a paid cache.
- Concurrency and rate limits must be measured against the free instance before rollout.

### FR-008 Shared Finance Pipeline

Extract runtime-neutral modules that Render and local verification can reuse for:

- image validation
- OCR normalization
- deterministic parsing
- source inference
- Finance rule evaluation
- duplicate assessment
- candidate construction
- auto-confirm eligibility
- processing-event generation

Shared modules must not depend on `NextRequest`, `NextResponse`, React, browser APIs, or route-local cookies.

### FR-009 Source Inference

- Send and sanitize the original filename because it is useful evidence.
- Treat filename evidence as a hint, not a sole authority.
- Require an independent OCR-derived signal for the same source before selecting it from filename evidence.
- If source signals conflict or only the filename matches, leave the source unresolved for review.
- Persist the source-detection signals used in the decision.
- Update the existing source-selection algorithm so a filename match is not assigned before corroboration.
- Extend the source-evidence type deliberately before introducing any signal kind beyond the existing filename and OCR aliases.

### FR-010 Idempotency and Recovery

- Continue using a per-user image hash to identify exact screenshot retries.
- One intake may produce at most one active candidate.
- After validation and capacity admission, begin the intake before OCR with a bounded processing lease. This stores metadata and state, never screenshot bytes.
- Change the current duplicate-intake contract: an existing terminal intake should return or recover its existing result, an active lease should return an explicit retryable state, and an expired lease should permit safe manual reprocessing.
- A retry after an ambiguous network failure must recover the existing intake lineage when possible instead of returning only the current generic duplicate conflict.
- Define a processing lease or stale threshold so an interrupted request cannot block the same screenshot forever.
- Replace the current sequence of independent OCR, candidate, event, and intake writes with a narrow finalization RPC or equivalent transactional state contract.
- The finalization contract must be idempotent for the same intake and must not overwrite a terminal result with a late request.
- Final confirmation must keep the transactional duplicate recheck.
- A replay must not create a second ledger transaction.

### FR-011 Response Contract

The Render OCR route should preserve the current upload response contract. A review result has a pending candidate and no transaction:

```json
{
  "data": {
    "intake": {},
    "candidate": {},
    "transaction": null,
    "auto_confirmed": false
  }
}
```

An eligible auto-confirmed result has a non-null transaction and `"auto_confirmed": true`. The response must also retain the current warning and recoverable variants where applicable. The browser should not need a second API merely to obtain the newly created upload result.

### FR-012 Warm-Up

- `/warm` must be a non-blocking optimization, never a navigation dependency.
- Never await warm-up as part of login or page navigation.
- Warm when the Finance add page opens or the Screenshot entry mode is selected.
- Warming after authenticated login or dashboard mount remains an explicit product decision.
- A single warm request does not keep Render alive indefinitely.
- Do not send periodic artificial keep-alive traffic.
- Authenticate, authorize, and rate-limit `/warm`.

### FR-013 Strict CORS

- Allow the production origin `https://idea-dump-alpha.vercel.app`.
- Allow only explicitly configured localhost development origins.
- Do not use wildcard origins with credentials or authorization headers.
- Permit only the methods and headers required by OCR and warm-up.
- Handle unauthenticated `OPTIONS` preflight only for configured origins. Preflight must not initialize Tesseract, invoke Finance authorization, consume OCR capacity, or process a request body.
- Send `Vary: Origin` where the response depends on the request origin.
- Treat CORS as browser containment, not authentication. Non-browser clients can bypass CORS.

### FR-014 Safe Logging

- Never log screenshots, access tokens, refresh tokens, API keys, or full sensitive OCR text.
- Log request IDs, verified user IDs only where operationally necessary, intake IDs, stage names, durations, safe error codes, and resource measurements.
- Separate user-safe errors from internal diagnostic details.

## Authentication and Database Access

### Token Validation

Render must validate the Supabase access token before any expensive image processing.

Current official Supabase guidance provides two relevant methods:

- `auth.getClaims(token)` verifies signature and expiry against the project's JWKS and is the initial recommendation for efficient JWT validation. With symmetric signing it falls back to an Auth-server request.
- `auth.getUser(token)` performs a network request and returns an authentic, up-to-date user record when that record is needed. It must not be described as immediately invalidating an otherwise unexpired access token after logout.

Access tokens from revoked sessions can remain valid until their `exp` time. If this Finance operation requires immediate post-logout invalidation, additionally verify that the JWT's `session_id` still exists in `auth.sessions`; otherwise document acceptance of the normal short-lived JWT window.

Only the access token should cross from the browser to Render. The browser must never send its refresh token to Render.

### Current Live-Schema Constraint

The live Supabase project currently uses a server-only data-access posture:

- Finance and RBAC tables deny direct `authenticated` access.
- Existing Finance workflow RPCs such as intake begin and candidate confirmation are executable by the server role, not the `authenticated` role.
- The current Next.js APIs validate the user separately, then use an admin client with explicit user filters.

Therefore, "use the user JWT for all database writes" is not a drop-in configuration change. It would require a deliberate grants, RLS, and RPC redesign.

### Database Credential Decision

Two safe implementation directions remain:

#### Option A: Hybrid authenticated request with narrow privileged persistence

- Validate the user JWT and Finance access first.
- Use a separate server-only Supabase secret client only for operations that the current schema intentionally reserves for trusted services.
- Scope every query and mutation by the verified user ID and, after creation, the verified intake ID.
- Prefer narrow transactional RPCs for privileged state transitions.
- Never place the secret in browser code or a `NEXT_PUBLIC_*` variable.

This is the lowest-change path and preserves the current server-only database posture.

#### Option B: User-token and RLS redesign

- Grant only the exact table and RPC privileges needed by the authenticated role.
- Add ownership policies based on `(select auth.uid()) = user_id`.
- Ensure updates include both `USING` and `WITH CHECK` ownership constraints.
- Change RPC contracts to derive identity from `auth.uid()` rather than accepting an authoritative `p_user_id`.
- Reassess whether users should be able to call worker-facing mutations directly outside Render.

This keeps ordinary operations under RLS but is a broader security and migration change. It must not be implemented merely by granting existing server RPCs to `authenticated`.

The user JWT is mandatory in either option. A Render secret authorizes the service; it does not replace caller authentication or Finance module authorization.

## Security Requirements

### Public Endpoint Model

The Render service is public at the network level. Security requires all of the following:

- validated Supabase access token
- current Finance module authorization
- strict CORS for browser containment
- input-size and image validation
- per-user rate and concurrency controls
- explicit ownership filters or RLS
- no trust in client-supplied identity
- safe logs

A static API key embedded in the browser is not an acceptable substitute because users can extract it. If direct Supabase JWT validation is not used, the acceptable alternative is a short-lived, scoped upload ticket minted by Next.js after it authenticates and authorizes the user. That alternative adds another request and custom token machinery, so it is not the initial recommendation.

### Secret Handling

- Prefer a modern, separately rotatable Supabase secret key if privileged persistence is approved.
- Store secrets only in Render environment secrets.
- Never expose them through the browser, source control, logs, response bodies, or error reports.
- Keep user-scoped and privileged Supabase clients separate.
- Rotate a secret immediately if exposure is suspected.

### Sensitive Finance Data

- Use HTTPS only.
- Do not retain original screenshot bytes.
- Store OCR text only where the existing Finance product requires it.
- Avoid sending OCR text through unrelated services.
- Do not use OCR content, filenames, or user-editable metadata as authorization input.

## Free-Tier Limitations

### Render Free Web Service

Current official Render documentation states that free web services:

- receive 512 MB RAM and 0.1 CPU
- spin down after 15 minutes without inbound traffic
- may take about one minute to spin back up
- use an ephemeral filesystem
- may restart at any time
- cannot attach persistent disks
- cannot scale beyond a single instance
- do not support shell or SSH access
- consume a shared allowance of 750 free instance-hours per workspace per calendar month while running
- consume outbound bandwidth when sending responses or calling Supabase, with plan-specific allowances and possible billed overage when a payment method exists
- may be suspended for unusually high service-initiated public traffic

Implications for the current phase:

- OCR may be slower than the current 3.28-second observation.
- A cold start can dominate the user wait.
- The worker and any runtime cache are lost on spin-down or restart.
- Screenshot bytes cannot be recovered after a restart.
- Initial OCR concurrency must be one.
- A periodic keep-alive would consume free hours and undermine free idle spin-down.
- Singapore should be selected when creating the service to stay near the Supabase project in `ap-southeast-1`.
- Zero-cost operation requires bandwidth monitoring and an explicit billing-state check; do not assume Render's pipeline-minute spend limit protects bandwidth.

The service must be benchmarked with the supplied Ryt Bank screenshots and representative larger images before any UX timing promise is made.

### Supabase Free

The current phase uses the existing Supabase Auth and Postgres project but does not add Finance screenshot Storage or Queues. Database rows for OCR text, candidates, and events still consume database capacity.

The future reliability phase would additionally consume Storage, logged Postgres space for Basic Queue messages, Realtime or polling, webhook or `pg_net`, and retention capacity. Supabase does not document a separate Queue quota; these messages count toward the project's database allowance. Relevant free-tier limits must be reverified before that phase is approved.

### Vercel Hobby

The browser calls Render directly for OCR. Vercel continues to host the application but does not proxy screenshot bytes or wait for OCR inside a Next.js function.

### Cost Protection

- Do not create a paid Render worker or disk.
- Do not add a paid cache or OCR API.
- Monitor Render instance-hour and outbound-bandwidth usage.
- Verify whether the Render workspace has a payment method and which workspace plan and bandwidth allowance apply before rollout.
- Configure available alerts and stop or disable OCR before a billable bandwidth threshold. Do not assume a general Render spend cap exists for bandwidth.
- If OCR is unavailable, preserve manual Finance entry as the safe fallback.

## Failure Modes and Required Responses

| Failure | Required current-phase behavior |
| --- | --- |
| Invalid or expired access token | Return `401`; do not parse the image or run OCR |
| User lacks Finance access | Return `403`; do not run OCR |
| CORS origin is not allowed | Do not emit an allow-origin header; reject where appropriate |
| Request exceeds byte limit | Return `413` before OCR |
| MIME, magic bytes, or dimensions are invalid | Return `415` or `422`; do not run OCR |
| OCR capacity is occupied | Return `429` or `503` with `Retry-After`; do not enqueue in memory |
| Render is cold | Keep the browser in a truthful waiting state; do not claim the request is queued |
| Browser disconnects before upload completes | No durable screenshot exists; user retries the upload |
| Render restarts before the intake lease is created | No durable OCR state exists; the user manually retries the upload |
| Render restarts after the intake lease but before finalization | Screenshot is lost; lease expiry must allow the same intake lineage to be reprocessed |
| Render writes data but the response is lost | Retry resolves through image hash and existing intake lineage |
| OCR worker fails | Reset the shared worker and return a safe retryable error when recovery cannot complete |
| OCR text is unreadable | Record a safe terminal state where an intake exists and return a user-readable failure |
| Duplicate is detected | Return review payload with duplicate evidence; do not silently create another transaction |
| Supabase mutation fails after candidate creation | Recover the saved candidate into review where possible |
| Free-tier capacity is exhausted | Fail visibly and preserve manual entry; never upgrade automatically |

## Observability

Record enough information to answer:

- Was the service cold or warm?
- How long did authentication, module authorization, upload, worker initialization, OCR, parsing, duplicate assessment, persistence, and response take?
- What was the accepted byte size and decoded pixel count?
- Was the request rejected for authentication, validation, rate, concurrency, OCR, or database reasons?
- Was an existing intake recovered after an ambiguous retry?
- How often are users forced to re-upload?

Useful metrics include:

- request count by safe outcome
- cold-start and worker-initialization duration
- OCR duration and confidence
- peak memory during representative images
- active OCR count and overload rejection count
- duplicate and idempotent-recovery count
- stale processing intake count
- `/warm` request and success count
- Render free instance-hour consumption

Do not include screenshot bytes, bearer tokens, API keys, or full OCR text in logs or metrics.

## Rollout Proposal

### Phase 0: Isolated Render Benchmark

- Deploy a Render Free proof of concept in Singapore.
- Run the existing Ryt Bank screenshots and representative accepted sizes.
- Measure cold start, model initialization, warm OCR, total duration, and peak memory.
- Verify native Node compatibility and the 512 MB limit.
- Do not connect the proof of concept to production Finance writes.

### Phase 1: Shared Processing and Service Contract

- Extract runtime-neutral validation and Finance processing modules.
- Add reusable Tesseract initialization with one-worker concurrency.
- Define authenticated OCR, warm-up, health, CORS, and response contracts.
- Add a feature flag capable of selecting the current Next.js path or the Render path during validation. Whether the Next.js OCR path remains an exposed pilot fallback is decided separately.
- Verify identical parser, rule, duplicate, and candidate results against representative fixtures.

### Phase 2: Owner-Only Direct Upload Pilot

- Enable direct browser-to-Render OCR for the owner account only.
- Apply the selected database credential model.
- Validate authentication, Finance authorization, idempotency, stale-intake recovery, overload behavior, and safe logging.
- Validate progress states and manual re-upload behavior.
- Keep manual Finance entry available.

### Phase 3: General Direct Upload Rollout

- Enable the direct flow for approved users with Finance module access.
- Retain a global feature flag and rollback path.
- Monitor latency, cold starts, forced re-uploads, free-tier consumption, and database growth.
- Do not add Storage or Queues unless the future-phase criteria are met.

### Future Phase: Durable Asynchronous Reliability

Supabase Storage and Supabase Queues are explicitly deferred. Consider this phase only if usage shows that one or more of the following matter enough to justify the complexity:

- users need to close the browser immediately after upload
- repeated manual re-uploads cause meaningful friction
- Render restarts or network failures lose too many jobs
- OCR volume requires durable backpressure
- automatic retry becomes a product requirement

The future architecture would:

1. Upload screenshots to private temporary Supabase Storage.
2. Create an authoritative intake and a durable Supabase **Basic Queue** message containing only an opaque intake ID and processing version. Do not use an Unlogged Queue for durable work.
3. Send a best-effort wake signal to the Render web service through an authenticated Database Webhook, `pg_net`, or approved recovery trigger. The queue and intake remain authoritative because the wake signal itself is not durable.
4. Have Render `read` a message with a visibility timeout longer than expected processing, extending it with `pgmq.set_vt` if necessary.
5. Download and revalidate the image, process it idempotently, then `delete` or `archive` the message only after durable success. If processing fails or the service restarts, the message becomes visible again after the timeout.
6. Expose asynchronous status through bounded polling or Realtime.
7. Delete temporary screenshots according to an approved retention policy.

That phase will require a separate approval covering retention, retry limits, queue visibility, recovery wakes, cleanup, polling or Realtime, and free-tier quotas. It must not be partially implemented in the current phase.

## Current-Phase Acceptance Criteria

- The browser uploads accepted Finance screenshots directly to Render, not through Next.js.
- Every OCR and warm-up request is authenticated and Finance-authorized.
- Render derives ownership from verified identity and never trusts a body `user_id`.
- PNG, JPEG, and WebP files are limited to 4 MB and validated by content and decoded dimensions.
- Screenshot bytes are never persisted to Supabase Storage or Render disk.
- One warm Tesseract worker can be reused safely across serialized requests.
- Excess concurrent OCR work receives a bounded retryable response instead of entering an in-memory backlog.
- The existing parser, rules, duplicate assessment, candidate review, and confirmation policies remain correct.
- Filename evidence is preserved but cannot be the sole authoritative source signal.
- The browser receives the existing upload payload shape, including review, auto-confirmed, warning, and recoverable variants.
- The UI distinguishes uploading, reading, and preparing-review phases.
- Cold starts are represented honestly.
- Ambiguous retries do not create duplicate candidates or transactions.
- Interrupted processing eventually permits a manual re-upload of the same screenshot.
- No paid Render service, paid cache, persistent disk, or paid OCR provider is required.
- Manual Finance entry remains available when OCR is unavailable.
- No screenshots, credentials, or full sensitive OCR text appear in logs.

## Decisions Requiring Approval Before Implementation

The architecture direction is now recorded as **direct browser-to-Render OCR in the current phase, with synchronous waiting and possible manual re-upload accepted for that phase, and Supabase Storage and Queues deferred to a future reliability phase**. The following implementation decisions remain open:

1. **Database credential model:** hybrid JWT validation plus narrow server secret, or a deliberate user-token/RLS redesign.
2. **Warm-up trigger:** Finance entry only, or both authenticated dashboard/login and Finance entry.
3. **Image pixel limit:** retain or lower the current 25-million-pixel maximum after the Render benchmark.
4. **Overload response:** choose `429` or `503`, the `Retry-After` policy, and client retry behavior.
5. **Stale intake recovery:** choose the processing lease or stale threshold for safe manual retries after a restart.
6. **Auto-confirmation:** retain current automatic confirmation for eligible OCR results or always send Render-produced candidates to review during the pilot.
7. **Pilot fallback:** keep the existing Next.js OCR route as a manual feature-flag fallback or disable OCR when Render is unavailable.
8. **Render packaging:** native Node runtime is preferred initially; use Docker only if reproducible native-runtime constraints require it.
9. **Review navigation:** show success in place, link to review, or navigate automatically after a candidate is prepared.

No production-connected implementation should begin until these decisions are reviewed. The isolated Phase 0 benchmark also requires explicit approval and must confirm that Render Free is viable before the owner-only pilot begins.

## Alternatives Considered

### Supabase Storage and Queue in the Current Phase

Deferred rather than rejected. It provides durable retry, asynchronous completion, and backpressure, but requires temporary-image lifecycle rules, queue claims, wake and recovery logic, status delivery, cleanup, and additional security policies before the product has demonstrated the need.

### Keep Synchronous OCR in Next.js

This is the lowest-change option and currently succeeds quickly for representative uploads. It retains Vercel-side CPU pressure, image proxying, per-request Tesseract initialization, and request-duration coupling.

### Supabase Edge Function Runs Tesseract

Not recommended for this workload because Tesseract is CPU- and memory-heavy and worker compatibility is a poor fit for constrained Edge Function execution.

### n8n Orchestration

Rejected for the current phase. It adds another runtime, authentication surface, and resource consumer without removing the need for durable image storage, idempotency, or a suitable OCR compute host.

### Paid Render Background Worker

Operationally stronger but incompatible with the zero-cost constraint.

### External OCR Provider

Potentially faster or more accurate but rejected because free quotas can be temporary, require billing setup, or create paid-usage risk.

### Browser Tesseract

Rejected because it consumes user CPU, memory, battery, and data and produces device-dependent performance.
